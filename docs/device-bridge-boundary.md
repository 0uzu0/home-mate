# 设备网关与底座边界

决定日期：2026-11-07。状态：用户已同意该架构方向；本文件记录职责与验收要求，尚未定义通信schema或实现代码。

## 1. 架构决定

Home Mate核心采用模块化单体；具体型号的设备桥是外部独立组件，独立维护、测试和发布，通过版本化设备协议接入。Home Mate仓库不内置Dot等品牌桥的实现，不导入旧RUI或桥的内部对象。

这替换了此前“Dot Rust适配器可直接放在主服务内部”的建议。新工程正式名为 **Home Mate Device Gateway**，简称设备网关；接手Agent须新建独立私有仓库`yes999zc/home-mate-gateway-linux`，以Rust从零实现，不沿用旧桥工程。建仓步骤见[设备网关工程交接](device-gateway-project.md)。本文保留历史文件名及部分“桥”的通用表述，均指该外部设备边界，不表示继续开发旧桥。具体依赖和部署方式待验证；独立不要求远程部署，允许与底座作为独立进程运行在同一 NAS，也适用于后期两者同在音箱的实验。

底座定义语音终端抽象和接口合同；桥将设备行为映射到合同。协议文档、schema或小型SDK可共享，但桥不能依赖底座内部模块、配置对象、数据库或Python类。协议版本与组件版本分开管理。

## 2. 职责划分

设备接口是按可选能力接入的通用边界，不限定音箱。文本/事件客户端、ESP32板和摄像头可以只声明自身能力；音频、AEC、播放、图像及动作各自协商，不存在的能力不要求实现。以下音频行仅适用于具有相应能力的设备，详细分类见 [通用接口](interfaces-and-tool-layer.md)。

| 具体设备桥负责 | Home Mate底座负责 |
|---|---|
| 厂商协议、握手、控制/数据连接、硬件重连与固件兼容 | 注册、身份/房间映射、协议兼容检查、设备就绪与不可用处理 |
| 解释固件实际交付的音频布局、参考来源与已完成的处理，按需要执行设备补偿 DSP | 按协商合同接收音频，组织通用唤醒、分段、识别和对话管线 |
| 设备音量刻度、dB映射、物理限制、硬件参数的验证和应用 | 表达目标音量或相对调整，核对操作范围，接收实际值与结果 |
| 实际播放、结束、flush与设备侧停止语义 | 播放任务、暂停/替换/取消、执行代和迟到结果处理 |
| 按键、物理静音、灯光等设备事件的协议翻译 | 依据通用语义组织任务与交互，不从品牌推断行为 |
| 固件能力、实际音频路径、处理状态、硬件诊断 | 检查所需能力、显示有效状态和降级原因，不把请求当已应用 |

现有 Dot 路径在固件内完成七麦融合，上行已是一路融合 mic 加一路 ch8 参考。Dot 适配模块核对协商格式并转交这两路，在诊断中注明融合位置。通用网关按每种设备实际提供的能力工作。逐台记录见[设备基线](dot-device-baseline.md)。

大脑负责用户意图、上下文与行动选择；桥不解析完整用户请求，也不调用业务工具。任务归属和生命周期由底座管理，桥按任务/流身份执行并报告自身事实，不另建竞争的任务真相。

## 3. 接口需要表达的事实

后续协议设计至少覆盖以下语义；具体字段、传输方式和时间预算仍待设计：

- 协议版本、稳定设备身份、桥实例/连接代、能力和不支持项。
- 可选能力、媒体类型与实际模型/引擎支持；图像来源/时间/访问范围和媒体生命周期不能伪装成音频字段。
- 对于音频能力：期望音频模式、协商结果、实际应用路径，采样率、格式、通道标记、时间/序号来源。
- 输入音频、参考可用性、处理与旁路状态；不能只声明“支持AEC”。
- 播放、暂停、恢复、停止/flush、音量与物理静音的请求、接受、应用、失败/不确定结果。
- 任务/音频流标识、执行代、断线和重连后的重新绑定，旧连接事件与取消后数据的拒绝规则。
- 播放进展和各级回执；提交、网络发送、设备接收/消费分别表达，缺失保持未知，不承诺人耳已听到。
- 有界缓冲、背压、超时及失败行为，避免多一层桥导致无界排队或无法停止。

停止播放时，底座立即停止向旧任务提交数据。网关区分停止请求已发送、设备已确认清空以及结果未知。若设备协议只证明写入成功，回执只记录到写入这一步。重连后收到旧回执时仅更新所属任务的记录。

底座可以有通用协议客户端与虚拟终端实现，但不出现“如果型号为Dot就发特殊命令”之类核心分支。设备名称、型号标签、配置数据、文档及合同测试样例中出现品牌，不等同于实现泄漏。

## 4. AEC和声学处理的边界

支持两种候选接入形式，首期选择及实现位置需通过N1确定：

| 形式 | 桥交付内容 | 底座责任 |
|---|---|---|
| 麦克风＋参考 | 格式/对齐/来源明确的mic与ref，实际处理状态 | 通过通用音频引擎完成AEC，不能依赖设备型号判断 |
| 已处理语音 | 设备或桥音频前端已处理的mic，处理/旁路/退化状态，按合同提供诊断信息 | 使用明确的处理状态，不重复启用同一阶段AEC |

原始硬件差异由桥侧吸收；桥的音频前端可以运行在设备，也可以运行在NAS桥进程。成熟算法库可以复用，不要求每个桥重写算法。

AEC处理所有者必须明确，所需参考及处理状态可验证；同一阶段不能由两边互相猜测后重复处理。能力支持、已请求、已协商、实际启用和当前有效性分别记录。参考空闲与参考失效也不能混为一谈。

底座保留通用对话时序、唤醒与接话、提示音保护和任务协调。若某种保护需要根据输入条件调整，应以合同能力/状态表达；不得因换AEC位置而悄悄关闭保护或改变当前模式。Home Mate已要求支持全双工、默认半双工，桥需通过通用合同报告并发收放音与处理状态，按 [语音交互规则](voice-interaction-and-control.md)验证切换。旧RUI的关闭决定不受影响。

## 5. 配置与管理页面

- 桥拥有型号物理约束、硬件映射、固件专属配置及适用的房间声学配置。底座拥有用户交互策略、任务范围与通用管线策略。
- 通用AEC若在底座运行，其算法参数由对应音频组件管理，并关联桥报告的输入profile；不能将所有声学参数强行归为设备固件参数。
- 桥提供可校验、可版本化的配置描述与实际生效状态。底座页面可通过通用接口展示/代理操作，不通过复制设备字段含义来维护专属表单逻辑。
- 配置请求、已保存和硬件实际应用分开；物理限制由桥验证，失败与不支持明确返回。
- 初期无需通用插件市场或任意前端脚本注入。参数描述格式与呈现范围后续确定。

## 6. 独立维护的验收条件

1. 没有安装真实设备桥时，Home Mate核心可以启动；使用虚拟终端验证对话与任务合同，不需要品牌库或设备凭证。
2. 新桥能脱离底座，通过协议测试端验证握手、帧布局、能力、配置、播放、停止和重连行为。
3. 现有接口已表达的能力，新增或修改音箱协议、固件兼容与音量映射时，仅修改并发布对应桥，底座核心无需出现型号分支。
4. 多种桥运行同一组基础合同测试，明确各自可选能力；不支持项不能假报成功。
5. 管理页面读取设备的能力、参数说明与有效状态，不硬编码Dot行为。
6. 集成验证覆盖断线、超时、未知结果、旧连接迟到、取消后数据、缓冲积压及能力不匹配，不只检查能连上和能播放。

核心无音箱时可提供助手文本/任务接口；无音频摄像头不需要启动AEC或伪造播放回执。品牌标签仍不进入核心逻辑。对第三方桥提供合同示例与独立测试端，许可/分发策略另核对。

新增硬件若带来合同从未表达的共同能力，可通过通用接口版本演进支持。不能承诺未来所有硬件永远无需改底座，也不能用厂商特例绕过协议演进。

## 7. 实施顺序和范围

首期硬件范围为 dot2-d（2026-11-07用户取消四房推广，其余三台Dot不再属于首期范围），逐台差异见 [Dot设备基线](dot-device-baseline.md)。LX06暂不开发或验收；未来是否支持及是否需要重做固件另行评估，不能以此扩展首期桥范围。

N1先设计最小设备合同，用虚拟终端与协议测试端核对，再实现外部Dot桥到Rust底座的隔离链路；结合[RUI经验迁移指南](rui-experience-migration.md)提取实际协议与声学条件。不要先搬整个旧桥，再逐层修补新底座。

真实模型与任务链路按HANDOFF首批并行推进。旧RUI及其Python桥继续由现有维护线管理，仅供只读参考。接手Agent已获授权新建设备网关私有仓库并开始隔离实现；本次文档更新尚未建仓或启动服务。何时接入实体设备、迁移音箱或生产发布，按后续范围执行。
