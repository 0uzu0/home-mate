# 语音交互模式与语音管理

决定日期：2026-11-07。产品定位：Home Mate家庭伙伴。用户明确要求从零设计时就考虑全双工与半双工配合，默认半双工，通过语音切换模式，并为换音色、参数调整和简单系统诊断提供语音入口。

> 2026-11-07更新：用户取消四房推广（部署顺序改为单房→音箱内同内核评估）。第7节"两房同时交互"等多房场景不再属于验收范围；单房仍适用的模式/音色/诊断/打断要求不变。助手正式名字为「高达」。

本文件记录产品与架构要求；交接时未实现或验证全双工。后续首批隔离开发按 [HANDOFF](HANDOFF.md)执行，不改变旧RUI当前关闭全双工的状态。

## 1. 已确定的产品要求

1. 全双工是Home Mate需要支持的核心能力，进入首期设计、技术验证和交付验收，不在半双工完成后再作为临时补丁添加。
2. 日常默认半双工，避免未经邀请加入家庭日常交谈。
3. 用户可通过语音进入全双工、回到半双工，且管理页面可查看实际模式并提供同等操作。
4. 用户可通过语音选择系统支持的音色；其他适合开放的参数有统一扩展接口，避免每种设置增加独立解析分支。
5. 用户可请求简单系统诊断，得到基于实际状态的简短说明；诊断与会改变系统的修复动作分开。
6. 语音、页面和开发Agent使用共同的管理能力、校验、应用与记录路径，实际结果一致。

## 2. 分开建模：音频双工、参与对话、主动发言

三个概念相关，但不能共用一个布尔开关：

| 维度 | 语义 |
|---|---|
| 音频双工能力/状态 | 播放时是否可持续处理输入、识别用户插话并及时停下或调整输出 |
| 对话参与状态 | 当前是否处于用户明确开启的会话，怎样唤醒、接话、退出和判断本次发言是否面向助手 |
| 主动发言策略 | 是否允许未经本次用户提问就发言；提醒等已授权任务按各自投递规则处理 |

默认半双工不等于关掉普通唤醒和有限接话。具体播放中可用的唤醒打断方式需定义，不把既有显式打断能力误删。

进入全双工应支持用户在助手说话时讲话和改变要求，但不自动表示允许全天回应所有环境人声。家庭交谈、电视/视频人声与用户对助手说话的区分，是独立的交互问题；不能仅凭VAD或“这是人声”认定面向助手，也不未经新决定引入声纹拦截。

具体参与判定、会话作用域、持续时长和自动退出规则留待N0.1明确。不能只把收音常开命名为“全双工已完成”，也不能许诺所有电视环境零误触。

## 3. 模式状态与切换合同

- 区分设备支持能力、用户请求模式、协商/配置结果和实际生效模式。桥/音频系统报告真实状态，模型不能自行宣布生效。
- 只有当前链路满足所需能力和AEC/参考等约束时才应用全双工；不满足时报告原因及实际保留的模式，不偷偷双开AEC或自动改固件。
- 语音和页面使用同一切换操作，明确目标设备/会话、作用范围、持久化要求和结果；未确定的默认作用域与跨房行为不猜测。
- 切换管理输入、输出、模型和工具任务的共同边界，拒绝旧代事件；不因模式变化复制音频、把旧提示音释放成新指令或重复设备动作。
- 回到半双工、停止当前输出是基础控制能力，不需要等待复杂规划结束；已发生的操作与可取消工作分别记录。
- 配置已保存、等待切换、实际应用、失败或未确认分别呈现。用户未要求时不擅自把临时会话选择写成永久默认。
- 断线、参考失效或能力退化后，不能维持虚假的“全双工正常”状态。具体暂停/降级及是否重新启用策略在N0.1/N1定义；任何降级可解释、可观测。

## 4. 统一语音管理接口

语音由大脑理解，再调用结构化管理能力。建议操作类别为“查询设置、修改设置、查询能力/可选项、诊断”；具体工具名和schema后续确定，不让模型生成文件路径或直接修改底层配置。

每个可开放设置需声明：

- 所有者、作用范围、类型、单位、允许值/范围及必要能力。
- 是否允许语音修改，是否仅查询；常用与高级设置分层。
- 临时/持久的选择、应用时机、是否需要重启/重连及影响。
- 当前请求值、实际生效值、结果与适用恢复方式。

模式、音色是明确需要的入口；不意味着所有AEC滤波长度、固件开关或内部调试参数都自动开放。扩展字段沿用共同接口与执行边界，不为每个参数写一套关键词路由。

目标或候选不明确时简短澄清；明确且允许的低影响设置直接执行，不为每次正常调整增加重复确认。对错误识别、否定、条件句、重复事件和权限范围按共同合同处理。

## 5. 音色切换

- 从当前TTS引擎真实可用音色中查询、选择；别名映射到实际音色ID，不能编造供应商不支持的名称。
- “换个音色”可结合偏好与候选，必要时给出少量选择；不要求用户知道底层ID。
- 设置在当前句、下一句、下一次任务还是下次启动生效，需要明确定义，并向用户说明；不要假报正在播放的已合成音频已被改变。
- 目标音箱/会话/全局范围、临时与保存默认的规则在N0.1明确。
- 更换音色可能改变ACK波形、时长和尾音。需验证提示音参考、裁切和自听保护仍适用；不能无条件复用旧音色的固定时间窗和模板。

## 6. 简单诊断

先提供基于已有观测的状态查询：当前设备/桥连接、输入新鲜度、模式、任务、模型/识别/合成引擎与工具的可用性、最近相关错误及阶段耗时。能力清单与诊断来源后续设计。

“检查一下为什么没声音”应说明已观测到哪些阶段、哪里异常、哪里未知，不凭模型常识直接认定硬件坏了。没有采集音频或新探测时，不声称已测过声学效果。

被动状态检查、主动测试播放/采样和实际修复是不同操作；重启服务、切AEC、刷机或改变其他房间不能悄悄混进简单诊断。需要进一步动作时按请求与既有执行规则办理。

语音只说相关摘要，详细记录在页面查看。凭证、私人音频与无关家庭对话不进入诊断播报。

## 7. 必须进入早期验证的场景

| 场景 | 检查内容 |
|---|---|
| 启动与普通日常使用 | 默认半双工，普通唤醒/有限接话可用，未受邀的环境声音不会因单个全双工开关获得执行授权 |
| 语音进入全双工再退出 | 请求与实际模式一致；否定/复合语句不误切换，页面及时反映结果 |
| 助手播放中用户插话 | 输入参考/时间轴正确，及时停止旧输出，保留用户句首，任务取消/修正不产生迟到动作 |
| 纯ACK/TTS与双讲 | 纯自声不成为新指令，真实用户重叠语音按模式处理；使用既有正反例并记录未知房间边界 |
| 家庭交谈与视频 | 分别验证双工能力与面向助手判定，不把视频人声当非人声可过滤；记录误参与与漏接 |
| 换音色后继续交互 | 实际音色存在、正确生效且可查询；ACK参考与尾音保护不沿用错误假设 |
| 重连、静音、参考失效 | 模式报告与实际链路一致，退化状态可见；语音不能越过物理静音，失败可通过页面/设备入口处理 |
| 两房同时交互 | 模式、音色、任务和配置范围不互相污染，除非用户明确要求共同操作 |
| 请求诊断或参数调整 | 语音与页面结果一致，不把查询升级成未请求的修复或全屋配置修改 |

模型理解与底座确定性合同分别验证，复用历史音频、虚拟终端和故障注入。模拟/实际安装/真实房间证据分开。全双工稳定性与有效识别尚未验证，不据设计文档宣布可用。

## 8. 对开发顺序的影响

- **N0.1**：将双工、参与策略、语音模式切换、音色和简单诊断列为明确产品要求；定义作用域、退出/持久化、故障降级和首批可语音修改设置。
- **N1**：验证并发收放音、参考/AEC、取消、模式状态与桥合同；Agent内核调研加入运行中控制能力及实际语义核对。
- **N2**：最小完整链路加入语音管理操作与真实页面状态，至少模式切换可形成端到端合同。具体音色/诊断的先后在首批范围中排定，不能无限后置管理入口。
- **N3/N4**：逐步验证音色与参数影响、环境干扰和四房范围；全双工进入产品验收而非被遗忘为未来补丁。能力未通过时明确缺口与阶段状态。

本需求对新Home Mate明确要求支持全双工，取代此前“新项目全双工是否支持另行决定”的未定表述。旧RUI全双工仍按原决定关闭；本轮不改代码、配置、固件或运行模式。
