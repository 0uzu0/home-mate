# Home Mate 架构原则与讨论共识

更新：2026-11-16。项目名称为 Home Mate。Rust 核心与 Vue 控制台已经在音箱上运行。本文件独立于现有 RUI。实施顺序与未定事项见 [新项目规划](plan.md)。当前范围与状态以 [HANDOFF](HANDOFF.md) 为准。

**当前范围（所有者 2026-11-16）：** 项目已在跑：五台 Dot2，每台一个核心，网关只走本机回环。多房间是正式功能。`deploy/home-mate.service` 只是 NAS 时代的存档，不可安装。下文里「首版在 NAS 上」「四房尚未开始」是 2026-11-07 的讨论记录，不再表示现在的部署。不要照旧交接去说「还没有运行时实现」。

## 已确定的方向

- 独立新项目，从零设计，不继承 RUI 的代码结构、补丁链和依赖选择。
- 继承旧项目经过验证的设备知识、房间参数、故障经验和验收场景；迁移前说明适用条件，不直接照搬全部配置。
- 采用“大脑＋底座＋硬件插座＋工具插座”的职责划分。
- 定位家庭伙伴：全双工进入首期设计与验证，默认半双工；语音可切换模式、换音色、调整适合开放的参数并做简单诊断，和页面共用管理接口。详见 [语音交互与管理](voice-interaction-and-control.md)。
- 长期可维护和可演进是核心要求，语言选择服从这些要求。
- 项目计划商用，依赖与分发许可进入选型和交付；自有授权方式待用户决定，见 [许可规划](commercial-licensing.md)。
- 核心提供通用助手服务，音频/播放为可选能力；不接音箱也可通过文本、事件或图像接口使用。ESP32/摄像头能力设计不扩张首期真实硬件范围，见 [接口与工具层](interfaces-and-tool-layer.md)。
- 硬件是同一型号与固件谱系，不是几台声学一致的音箱。音量上限、混音电平、VAD 阈值逐台测量、不跨台复制。每台一个核心，多房间有效。以后的定制硬件由网关适配，不在大脑里分叉型号。LX06 仍未接入。设备基线见 [Dot设备基线](dot-device-baseline.md)，那是当时的证据，不是现网保证。

## 本轮新增的架构共识

- 核心采用模块化单体、设备网关外部独立：Home Mate一个主服务，核心内部按职责组织；外部工程正式名Home Mate Device Gateway，由接手Agent新建`home-mate-device-gateway-b`私有仓库从零实现，独立维护、测试和发布，通过版本化协议接入。旧桥仅供经验参考；详见[设备网关工程交接](device-gateway-project.md)。必要的音频/推理隔离按实际需求决定。
- Rust作为核心服务首选；模型对话与工具循环也可在Rust内实现。Python只在关键引擎确有需要且边界清楚时引入；语言收益不等于智能或声学问题已解决。
- Agent内核优先Rust原生组件或小型实现，不默认额外引入跨语言服务；允许学习Pi等项目的上下文、工具钩子和事件机制。框架与自研按总维护成本选择，详见 [内核调研](agent-kernel-research.md)；M3.5 选型结论（2026-11-07，经独立评审）：自有循环＋自写客户端，genai 0.7.3 为已验证替换路径，见 [kernel-selection](kernel-selection.md)。
- 管理页面沿用Vue＋TypeScript方向，管理接口属于Rust服务；TypeScript并非旧RUI没有的新技术。
- 通过公开接口和结构化事件协作。状态有明确所有者；拆文件的目的在于职责与依赖清晰，不能只按行数机械拆分。
- 统一中枢允许明确请求走快路径；快路径与模型路径共享执行、权限和事实记录，含歧义或复合要求时交回共同决策入口。
- 管理页面从最小完整链路起随功能交付，用户能自行管理常用配置、查看有效状态和排查，不能依赖Agent直接改文件。
- 开发按需求/初步设计→技术验证→首批合同→完整链路→功能批次推进；设计、自动检查、独立评审与阶段验收按风险落实。具体见 [开发与交付流程](development-and-delivery.md)。
- 目标是“找得到、改得动、验得清”：新增设备或工具尽量局限于对应适配器；修改一项行为不应穿透全系统。

下列条款将共识展开为设计与评审依据。部署顺序见规划第三节，接口细节、参数、目录、依赖包和打包方式需后续设计及验证；设备桥外部独立的边界已确定；不能把示意结构当成已经确认的实现。

## 1. 每一种决定有明确归属

- 大脑负责用户意图、对话上下文、目标与约束、工具选择、任务调整和结果相关性判断。
- 底座负责连接、状态、资源、任务执行、取消、音频交付与真实回执。
- 外部设备桥负责硬件协议和能力差异，实现底座定义的版本化接口；核心不导入品牌实现或桥的内部对象。
- Home Mate定义统一工具合同，工具声明能力并查询/执行，返回结构化结果。MCP是适配协议，HA是能力后端，均不能取代共同执行边界。
- 用户决定优先于系统计划。大脑统一组织行动，执行层继续核对权限、设备范围和任务有效性。

同一语义不能由多个模块各自维护一套解释。需要多层检查时，必须说明各层检查的是意图、权限还是执行事实。

### 运行位置与决定权

每台音箱运行自己的核心。模型提出回复或工具调用，内核持有会话，底座执行并核实结果。ASR、TTS 和 LLM 分别经各自的服务接口接入。供应商端点和凭证由管理配置提供。硬件访问留在本机网关，网关拨回环上的核心。

多房间是正式功能：同一句话由各音箱自己广播声明，用同一套规则选出一台应答。用户随后提出的每项动作仍须经过任务与工具的权限和范围检查。同一动作应防重复提交。不同房间的独立请求不能因同一时间到达就被合并。NAS 上集中跑一个核心、再遥控多台音箱，是旧形态。

## 2. 先定义边界，再实现内部

组件明确输入、输出、状态、错误、超时与取消行为。调用方通过公开接口使用能力，不访问另一个组件的内部变量、文件布局或私有方法。

接口适度保持稳定，内部实现允许替换。核心模块不强制独立服务；设备桥已确定为外部独立组件，可与底座同机部署，不能因此依赖底座内部状态。具体职责、AEC形式和独立验收见 [设备桥与底座边界](device-bridge-boundary.md)。

## 3. 大脑能够演进，底座保持独立

替换模型供应商、提示词或 Agent 实现，原则上不修改设备协议和声学参数。

接入已被通用合同表达的新硬件，通过外部桥和能力描述完成，不在核心增加设备型号分支。新共同能力可推动接口版本演进，不能承诺所有未来硬件零修改。

新增工具，原则上增加能力说明、接口与对应验证，不要求在多个入口补关键词。大脑按请求使用能力，允许澄清和明确报告能力不足。

“原则上”遇到例外可以调整，但须说明原边界为何不足，并修改共同接口，避免暗中穿透模块。

## 4. 保持一个目标和上下文的来源

目标、约束、用户修正、任务关系、房间范围与执行记录各有明确所有者，其他组件使用查询或事件获取信息。

快速执行路径与模型路径共享同一执行接口和结果记录。快路径只处理可唯一确定的请求；复合、否定、条件与上下文歧义交由共同决策入口处理。

音频双工、当前对话参与和主动发言策略分别建模；全双工不自动授予回应所有环境人声的权限。

各房间上下文隔离，共享信息显式声明；不能默认把所有设备历史合并，也不能在没有身份依据时把所有声音当成同一用户。

## 5. 事实和推断分开

检索候选、模型生成、提交播放、实际发送、设备回执分别记录。没有观测到的状态保留未知，不通过改名或模型口头确认变成成功。

工具执行成功与用户目标完成分别判断。检索无匹配时不能悄悄删除内容类型、歌手、房间等用户约束，并用无关结果代替。

## 6. 任务生命周期明确

收音窗口、一次模型调用、一次对话回合、持续任务分别管理。

暂停、继续、插问、修正、替换、停止、断线和重启具有明确语义。底座接受取消后立即使旧任务失效，停止提交新音频和设备动作，并向设备请求清空已发缓冲。设备实际停止以相应回执为据，断线或缺回执时保留未确认状态。迟到结果只补记原任务的事实，重复事件按任务身份处理。

任务所有者、执行代和状态转换集中表达；避免每层维护不一致的 playing、busy 或 done 标志。

## 7. 音频路径有独立运行预算

连续音频不依赖模型及时返回。耗时推理、网络等待和阻塞任务不能阻断采集、参考信号、播放与停止处理。

队列有界、超时可见、积压有处理策略。记录各阶段延迟与资源占用，再决定隔离进程或优化语言；不以语言本身承诺实时性。

## 8. 参数与设备知识是正式资产

设备型号能力、具体设备、房间覆盖与应用策略分层表达，覆盖顺序明确，可查询最终生效值及其来源。

重要参数关联固件、信号路径、单位、取值范围、验证证据和调整原因。区分实测、模拟、假设和否决方案。配置格式可校验、可版本化，迁移不静默丢字段。

旧参数只在适用条件成立时复用；新架构不能继承未经证实的“全部对齐”或“问题已解决”结论。具体提取与验证按 [RUI经验迁移指南](rui-experience-migration.md)执行。

## 9. 源码直接表达最终行为

采用正常模块、显式依赖和可追踪配置。不以字符串替换源码、运行时修改类方法或隐藏全局状态作为日常扩展方式。

新增机制替代旧机制时，明确撤除旧入口和兼容代码的条件，避免长期叠加多个决策中心。代码生成若确有必要，须有固定输入、明确用途和可检查输出。

不以目录数量、抽象层数或使用某个框架证明架构先进；每一层应有实际职责和验证方式。

## 10. 围绕行为和边界验证

验收覆盖意图改写、补充约束、纠正、插问、失败换方法、取消、迟到结果和跨房隔离，不只检查标准口令与固定回复。

模型选择质量、确定性执行合同和真实设备声学效果分别验证。重要功能批次由未参与实现的Agent独立评审，必要时增加独立验证；受影响检查需完成，未失效结果复用，不按每个小改动重复全量验收。复用历史录音与有效结果，避免重复要求用户陪测；新行为不能只靠单条成功对话宣布完成。

## 11. 可观察，但维护负担受控

能追踪识别文本、当前目标、选择的动作、执行结果和阶段耗时，足以回答“刚才发生了什么”。不依赖保存模型内部思考，不把敏感凭证和私人音频混入普通日志。

维护文档围绕当前架构、接口、运行状态和未解决问题组织；历史证据有明确位置，不让多份“最新结论”竞争。

## 12. 为已知变化保留空间

优先支持更换模型、接入设备与工具、修改房间参数和扩展任务类型。初期不为所有假想需求建立多Agent、微服务或通用插件市场。

语言选择依据：核心依赖能否接入、类型与并发约束、性能需求、测试与诊断能力、构建部署复杂度，以及实际开发维护能力。目前首选Rust；关键链路验证后确认，必要的外部引擎通过明确接口接入，不因语言偏好重写成熟算法。

新增跨语言边界须有明确收益，同时评估协议、构建、诊断和部署成本。

## 13. 用户可自行管理，页面与服务一起交付

常用配置与排查是产品功能。页面读取真实管理API，展示有效值及来源、影响范围、保存/应用结果与失败原因；提供近期变更和适用配置恢复，不把未知显示为成功。

接口先约定，页面可用合同模拟数据开发，但本批须尽早接真实接口。核心逻辑、管理API、相关页面与行为验证按功能共同完成；只有脚本/API或模拟页面时标记对应部分完成，不能冒称用户功能已交付。

用户语音与Agent修改日常配置使用同一管理接口，遵循相同校验、生效反馈与变更记录。模式、音色和诊断提供真实能力入口，未明确开放的内部参数不自动全部开放。模型/设备内部调试不必全部变成页面；高级参数与常用操作分层，不在页面复制硬件业务逻辑。

## 14. 通用接口与商业生态

接口按能力、身份和状态建模，不要求所有客户端具备麦克风/扬声器；没有音箱时核心可以提供文本和任务服务。媒体来源与模型感知能力分开，图像可接入不等于视觉理解已可用。

管理、助手、设备/媒体与工具接口分别定义；共享必要的身份与错误语义，不强制所有流量使用MCP。对外接入先有版本化合同、示例和独立测试方式，再按需要提供SDK。

依赖、SDK、模型/素材和服务条款按实际版本与发行方式核对；核心实现许可、接口规范授权和客户协议分开。未经决定不自行添加开源许可证或宣称依赖全部可无条件商用。

## 设计评审的共同问题

1. 这个决定由谁负责，是否已在别处做了一遍？
2. 新增一个设备或工具，需要修改多少个已有模块，为什么？
3. 用户改变要求、任务被取消或结果迟到时，会发生什么？
4. 我们记录的是实际观测、系统推断，还是尚未确认？
5. 新机制成立后，哪些旧机制可以退出？

原则可随证据修订。修订需说明原因、影响和迁移办法；通过明确更新保持架构一致，不靠临时例外逐步架空原则。
