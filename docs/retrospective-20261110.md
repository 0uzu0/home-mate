## 1. 这是一个什么产品（一句话与三句话）

**一句话**：一个自持在音箱里的大脑——用户说话，它在本地把声音收进来、在云端做理解与合成，
在设备上决定"什么时候停、什么时候听、什么时候说"，并且在控制台上让用户看见和改掉它的行为。

**三句话（架构）**：

1. **一个大脑 + 一个底座 + 两类插座**。大脑＝核心（`hm-core`，Rust，模块化单体）：理解意图、
   维护目标、组织工具、核对结果。底座＝同一进程内的任务运行器/语音管线/存储，负责"可靠执行
   并如实报告事实"。两类插座＝**设备插座**（设备网关，独立私有仓，版本化协议）与
   **工具插座**（统一工具合同；MCP 是接入协议，HA 是能力后端）。
2. **决策权在运行时，不在模型**。模型可以建议，但"停播/开窗/是否算打断/任务是否还有效"
   由核心的确定性规则判定，每条忽略都有如实理由（`answer_protect`／`episode_active`／
   `disabled`／`muted`／`media_playback_out_of_scope`…）。这是与端到端语音产品的根本分歧：
   Gander 那类把对话控制权交给模型，我们交给可解释、可配置、可接地的运行时。
3. **两仓边界＝协议，不是代码复用**。核心只认 v0 协议帧；设备网关吸收厂商差异（ALSA ABI、
   LED sysfs、按键、codec bring-up、AEC、KWS 旁路）。协议版本从 v0（握手/播放回执/停止/重连）
   → v0.2（上行音频/mic 会话/设备状态）→ v0.2.1（LED 状态）→ v0.2.2（取时）→ v0.2.3（换网）
   → v0.2.4（关键词）。每次加帧都带能力门禁与合同测试。

**为什么核心上音箱**（C 阶段，用户拍板）：家里只有音箱、三服务全云，是"可铺量"的前提；
Mac/NAS 每户一台不可发布。红利实测：首声 p50 3.20 s → 2.4 s（mic 不再过 WiFi ＋ 连接复用）；
代价：482 MB 内存的设备要同时跑 AEC＋KWS＋核心（实测可行：单核 35%、全机 busy 9.4%）。

**作废的数字（为什么）**：

- **"T5 3/3、P50 120 ms"**：判据是计数器增量，而实现自激把计数刷到 17，任何一轮都必然"有停"。
- **"首声 3.20 s 未达标＝链路慢"**：C 阶段同样链路测出 2.4 s，说明当时的瓶颈是云端合成排队，不是架构。
- **"R6：音量越低误触发越少"**：条件顺序＝预热顺序，混进了 AEC 收敛（本复盘新增）。
- **"尾音杂音仍在"**：用户澄清 0.0.6/0.0.7 已消除，交接误记——一条没有版本锚点的负面结论烧掉半天取证。
- **"T2 流式 ASR 不行"**：归因错误（模型与接线方式同变）；真相是起步上下文，300 ms burst pre-roll 把 CER 3.9–4.2% 拉回 1.1–1.7%。
- **VAD 误切历史 0/6**：素材在 `/tmp` 已失、口径是宽窗恒真——不可复现的指标等于没有。

## 4. 重大事故与根因

### 4.1 P0 整机反复复位（最贵的一次）

**现象**：设备每几分钟整机复位（`wdt_by_pass_pwk`），从"重 I/O 时偶发"恶化到"空闲也复现"。

**根因链（每一环都有日志/时序证据）**：armv7 固件（musl 1.2，64 位 `time_t`）每次
`clock_gettime` 打 **`syscall 403`（`clock_gettime64`）**——3.18 内核的 compat 表没有这个号 →
MTK `traps` 补丁打 24 行寄存器 dump（实测 2.29 次/秒）→ 写 `console=ttyMT0` 时 console 驱动
**关中断**排空 FIFO → 音频 SPI **100 ms 传输超时**（崩溃前最后一个 dump 与超时相隔 98.9 ms）→
厂商 `spi_data_read` 空指针（fault 0x10）→ 内核死在软中断 → 硬件看门狗复位。

**修法**（只动二进制，不动内核）：`clock_gettime` 走内核确实实现的 32 位 263；`Path::exists()`
（走 `statx`=397）改 `access(2)`；核心 `fs::metadata`（`statx`=291）改 open/lseek/read。

**为什么这么难**：交接文档写"`/proc/last_kmsg` 0 字节、无 pstore，所以没有现场"——实际连续三个
boot 都读到 64,622 字节完整崩溃链。**"没有现场"先怀疑取证口径**。另外有界环形缓冲里的"总数"
不能证明不再发生（饱和后计数会降），判据要取最新一条的 **age**。

**镜像级剩余（发布前必须）**：去掉调试串口 console、限制 traps dump、修厂商 SPI 错误路径。

### 4.2 T5 自激与"自问自答"

**现象**：用户说"一直卡"——打断后回答被切成碎句反复重来；有时设备把刚说的话转写回来当新指令。

**六个根因**（全部有 A/B 或日志）：
R1 自激不只在起播瞬间（AEC 残余整段播放里持续有"响且与参考去相关"的窗口）；
R2 窗口比段活得长（新播放还能被打断）；
R3 **整轮 vs 一句**的完成粒度（每句重读 stop_epoch，停止后下一句当全新一句照播）；
R4 前滚把设备自己的话送进 ASR（"我在。"＝上一句答案的残余）；
R5 阈值不可行（echo 与 near 的 corr 分布几乎完全重叠，任何阈值分不开）；
R6 高音量下限幅失真（84/127 4 次误触发 vs 60/127 0 次）。

**修法**：设备侧起播保护窗＋参考未锁定不报事实；核心侧应答保护期＋起播即关窗＋
**整轮纪元**（一次打断作废整轮剩余语句，事件流走完只为记账）；**前滚不再回灌 ASR**（代价＝首字可能丢）。

**教训的核心**：**"计数器动了"不等于"功能通过"**——自激类缺陷会主动把所有计数型判据喂成绿色。
判据必须写"一次输入→恰好一次动作→一次完整输出→之后静默窗口零新动作"。

### 4.3 Android(FireOS) → emOS 迁移

**为什么迁**：FireOS 上每个"接管"都要与 init/HAL 对抗且被 respawn 拉回（按键被 evdev 单读者饿死、
LED 被 ledcontroller 拉锯、PCM 被 HAL 抢）。换平台一次消灭整类冲突。

**迁移成本远小于预期**：内核镜像复用（ioctl 行为可提前在 FireOS 上答完）、init exec 链复用、
`/data` 的 WiFi 配置直接沿用（IP 无感回归）。**但**：emOS 服务 envp 无 PATH（脚本要自设）、
无 HAL 后 codec DAPM 要固件自己 bring-up（10 条 DAPM 路由＋amp 时序）、无 netd 要自己拉 lo。

**不可忘的规矩**：物理兜底门必须本机实测（本机 Mute 要按满 ~30 s，客厅机 5 s——不可类推）；
每次刷写前后整读 SHA 对照（字节级证明）；镜像级动作前先做本机还原演练。

### 4.4 ch8 竞态与"回环"的真相

现象：偶发"跨启动 ch8 静默"，mic 还在但 AEC 参考没了。加了开机哨兵（`boot-health`）与
playback_loopback 诊断后变成可观测：真机 corr 1.0。**ch7 最终定名**：不是麦克风——静音时
−120 dBFS 数字零、播放时比最热麦还热 14 dB；与 ch8 互相关 corr 1.0/lag 0、电平差稳定
−23.6…−24.1 dB（＝`>>4` 的 24.08 dB 量级），改音量比值不变 ⇒ **同一路环回的两个数字刻度**。
竞态本身在本轮 6 次重启中未复现，保持开放。

### 4.5 音量/限幅：从"说话太小"到"自己的声音像人"

链条：用户说"不是音乐大，是说话小" → 移植 RUI 的响度阶梯（分档 EQ＋限幅）→ 实测说话到达级
+5.5 dB → 但高音量下打断开始自激 → A/B 定位到 loudness 开关 → 用户要求修成"限幅安全"→
本轮重写限幅器（连续增益）**仍未达标**，保留关闭。

**真正的收获不是修好了，而是知道了下一步唯一能判定的实验**：净增益 0 dB 但过限幅器。
在此之前所有"调参数"都是猜。

### 4.6 收尾长跑抓到的两个新问题（尚未修）

3 h 长跑是 D 阶段最后一道验收，也是唯一一次"按用户真实用法连续跑"。它抓到两个前面所有
短测都没暴露的问题：

1. **固件内存每次打断增长约 1.7 MB**：新起 RSS 5.7 MB → 68 分钟工作负载后 267 MB；
   停掉负载就不再涨；单次播放、两次背靠背播放、一次唤醒都不涨，只有"播放→被打断→回答"
   这一回合会涨。**采集路径已被"空闲不增长"证明清白**。设备上没有堆分析器，定位要靠
   带计数的二分（第一刀＝`--barge-in off` 跑同一负载）。这是**发布阻塞**：471 MB 的设备
   在正常使用几小时后会 OOM。
2. **近端检测偶发误触发**：13 次事实里 1 次无人在说话（−42.4 dBFS、corr 0.21），
   而 12 次真实刺激全在 −27.6…−30.3 dBFS。阈值有 12 dB 空档 → 建议 `--barge-in-db -38`，
   但改标定必须重做一次真人打断验收，所以**只给建议不改**。

**收尾后半场把第 1 项追到底了**：四刀二分 + 记账分配器证明**程序没有逻辑泄漏**
（每次播放结束 `live = allocated − freed` 回到 0.41 MB，而 RSS 同期涨到 11 MB；断掉北向
后 RSS 三分钟恒定），增长与**播放时长**成正比、集中在整段 WAV 的 MB 级缓冲上 ⇒ 是 musl
分配器对大块的保留/碎片化。修法三选一（换分配器／复用大缓冲／整段播放改流式），
证据在网关仓 §1.6。第 2 项（近端误触发）也做了实验：把门限从 −45 提到 −38 **不成立**
（同一轮刺激 2 次停播、多一段 ASR），已退回 −45。

**方法论上的教训**（已进 LL D-80…D-84）：长跑要同时看设备侧与核心侧；测量脚本自己的
时钟假设也会造假（设备无 NTP，核心时钟比 Mac 慢 42.6 s，窗口整体错位 43 s → 9 个"幻影误触发"）；
**"RSS 在涨"先量 live bytes**，差值就是分配器滞留；**调声学门限前先看失败样本的分布**。

## 5. 方法论（可直接抄走的十条）

1. **先复现再修，同一测试证明**。时序 bug 用可控同步点（门控假件、async 一次性钩子）让旧代码
   **稳定失败**，保留失败断言输出，再用同一测试转绿。概率压测不算复现。
2. **判据写死在工具里**。`t5_bargein_verify.py` 把"一次说话→恰好一停→一段→一次一致 ASR→
   播完→10 s 零新停"写进脚本；任何一轮不满足就是 FAIL，计数型假阳性不可能再出现。
3. **仪表必须能关、且默认零稳态开销**。探针常开把 chunks/s 压到 8.8–11.3（正常 12.5–13.4）→
   改按需武装；`--aec-measure` 长期写 /data 与看门狗复位相关 → 长跑一律关。
4. **刺激源与设备同位**。要测设备自己的问题，刺激必须从设备的麦克风位置发出（摄像头外放），
   不能用 Mac 扬声器隔着房间。反过来，自放测 TDOA 是退化布置，不能据此说阵列没方向能力。
5. **口径先钉死**。延迟门限、CER 归一化、单核/四核 CPU、音乐素材响度、ERLE 摆位——
   每条数字旁边必须能写出量法。换门限能换出任何结论。
6. **一致的失败先怀疑测量链**。跨四层 shell 的 `grep 'keyword\":'` 因转义永不匹配，
   冤枉了三个模型；"全零命中"先让 ASR 读素材做质量仲裁。
7. **一行为一改动 + 显式路径提交**。两会话共用主仓时 `git add -A` 会把别人的 WIP 卷进提交
   （真实发生过）。`git add <path>`，禁 `-A`。
8. **需要人在场的测试清单**（这些永远不要写成"已验证"）：LED 物理发光/逐灯校准、
   音量键手感与音量弧目验、跟随窗提示音听感、真人声唤醒率与打断体感、音乐浸润与 trim 取值、
   物理兜底门按压时长、AP 配网的真实手机流程。
9. **交接写法**：修复类结论必须钉住版本号与时间（"v0.0.7 上用户确认已消除"），
   否则一条误记会让下个会话把已修问题立成头等。
10. **"未做"就写"未做"**。本项目的验收表里 `未验`/`未实施` 是允许的词，
    "基本完成"不是。

## 7. 如果从 0 重来（顺序、可省的弯路、必须保留的验收）

**顺序（按依赖，不按兴趣）**

1. **先定"谁拥有什么"**：核心/网关/工具三边界＋协议版本策略。本项目做对了，后面所有返工都小。
2. **先跑通文本回路**（模型＋工具＋取消＋trace），再接语音。语音的 80% 调试时间在时序，不在语义。
3. **尽早把设备做成"可观测"**：开机哨兵（mic/ch8/AEC 锁）、诊断端点、串口全通道、A/B 槽。
   没有这些，P0 那种事故会烧掉一周。
4. **AEC 必须在真实设备上测，且先冻结参数再谈体验**。ERLE→冻结→CPU→VAD，顺序不可反
   （改一个参数，后面全部重测）。
5. **打断分两层做**：设备侧关键词（反射，300 ms 级）→ 核心语义（160–240 ms 检测）。
   先做语义会得到一堆"看起来对、体感很糟"的假阳性。
6. **长跑放在所有音频改动之后**。本项目的 3 h 长跑排了三次才真正跑（每次都被新改动推翻）。
7. **体验类反馈要当场分解到机制层**："说话太小"→响度阶梯；"一直卡"→整轮纪元；
   "自问自答"→前滚回灌。不要直接照着感觉调参数。

**可以省的弯路**

- 不要在 FireOS 上与 init/HAL 抢资源（按键/LED/PCM/自启四处都撞过）；换 emOS 一次解决。
- 不要用 `afplay -v` 做声压衰减（这台 macOS 不衰减）；不要在 `/tmp` 放测量素材（会丢）。
- 不要相信模型的"自报延迟"（token 时间戳与声学位置可差 1.6 s）；延迟只能来自同线程同时钟的物理轨。
- 不要用能量阈值切真人语音做模型测试（会把应答音/退下词切进来，冤枉模型）。
- 不要在有界缓冲区上只调上限（TTS 比实时快 2 倍，10 s→60 s 只是把墙推远）；正解是发送侧配速。

**必须保留的验收（删掉任何一条都会在后面付出代价）**

- 一次说话 → 恰好一次动作 → 一次完整输出 → 静默窗口零新动作（打断）。
- 播放中自听段=0（门控＋盲窗＋AEC 余量），且"没人说话时不可能造出一句话"（前滚不回灌）。
- `chunks_per_sec ≥ 12` 的实时哨兵（软浮点库混入会静默变慢）。
- 复位判据看 trap **age** 与 uptime 连续性，不看计数。
- 每次交付都问一遍"控制台哪里能看到/改到"，答不上来就是欠账。
- 两仓测试全绿＋一次独立评审（本项目每次 REQUEST_CHANGES 都抓到了真问题）。

## 8. 本项目当前能做什么、不能做什么

**能**：唤醒（本地 ACK）→ 云端 ASR → 云端 LLM（双供应商兜底）→ 云端 TTS（流式）→
音箱播放；播放中说关键词或直接说话都能停；退下/跟随窗；控制台看改全部语音参数；
诊断（被动/主动探活/回环自检/7 麦）；固件与核心经 API 自更新。

**不能**（明确未实施，见 lessons-learned「未来计划」）：AP 配网、T1 说完判定、全双工常开、
HA 真实设备、真实音乐后端、LX06、端侧 ASR。
