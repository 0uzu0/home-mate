# 通用服务接口、工具层与第三方开发规划

决定日期：2026-11-07。用户要求Home Mate面向未来商用，提供通用服务接口，可接音箱、ESP32板、摄像头及其他客户端，接口契约和第三方开发指导需提前规划。

本文件确定边界与调研任务，传输栈、字段schema或SDK由后续隔离开发验证；当前执行范围见 [HANDOFF](HANDOFF.md)。首期真实硬件仍为四台Dot；ESP32/摄像头作为接口必须容纳的能力场景，不因此立即开发固件或接入实体设备。

## 1. 通用核心不依赖音箱

大脑接收用户输入与附件上下文，输出文本、任务事件或媒体结果。音频是可选通路；纯文本客户端、没有扬声器的板子、只提供图像的摄像头不需伪造麦克风、播放或AEC能力。

- 设备按能力协商，而非按品牌或“必须是音箱”分支：文本/事件、音频输入、音频输出、图像、视频或动作能力按需声明。具体能力名称后续定稿。
- 摄像头取图、授权/会话与视觉理解分开。收到图像不代表当前LLM支持视觉；模型适配层需报告能力，可选视觉引擎与主对话模型的关系后续验证。
- 原始设备协议及摄像头接入由外部桥/适配组件封装。核心消费标准媒体引用与元数据，不内置型号命令或默认所有摄像头支持同一协议。
- 大媒体与控制消息分离，明确类型、大小、时间戳、来源、有效期、访问范围与背压；不默认将持续视频或私有流地址塞入每轮模型提示词。
- 第一版至少用无音频客户端和虚拟图像来源验证核心不会依赖音箱启动；真实视频推理、ESP32固件和摄像头协议支持范围后续排期。

语音识别、语音合成与大模型各有独立的服务接口，可分别接入自建端点或付费服务。内核通过模型接口取得行动建议，再交给统一工具层校验并执行。识别与合成分别服务于输入和输出管线，用户可通过管理 API 和页面独立更换其中一项。[部署路线](plan.md#三部署路线与工程里程碑)

## 2. 工具层、MCP与Home Assistant的关系

| 概念 | 是什么 | 在Home Mate中的位置 |
|---|---|---|
| 工具层 | 项目对能力发现、调用、权限、执行、取消和结果事实的统一合同 | 由Home Mate拥有，供大脑和管理入口使用 |
| MCP | 外部工具/上下文能力的发现与调用协议，具有客户端/服务端角色 | 是工具/上下文适配的一条路径，不等同工具层或Agent内核 |
| Home Assistant（HA） | 家居实体、状态、动作与自动化的平台 | 是家居工具能力的后端，可通过HA原生接口或MCP接入 |

官方依据：[MCP架构](https://modelcontextprotocol.io/docs/learn/architecture)描述tools/resources/prompts等能力；[HA REST API](https://developers.home-assistant.io/docs/api/rest/)提供状态与动作接口；[HA MCP集成](https://www.home-assistant.io/integrations/mcp_server/)允许外部AI应用使用HA能力。

候选调用路径：

```text
大脑 → Home Mate统一工具合同/执行边界
                  ├─ 原生HA适配 → HA API → 实体/动作
                  ├─ MCP客户端适配 → 外部MCP服务器（可为HA）
                  ├─ 普通HTTP/本地工具适配 → 天气、音乐等服务
                  └─ 管理能力 → 模式、音色、配置与诊断
```

两条HA路径不要求同时启用。选型需比较目标HA版本实际暴露范围、状态/回执、权限、错误语义与维护成本；同一能力避免重复注册成两个相似工具。MCP中的成功响应或HA动作返回，不自动等于设备已达到目标状态。

HA官方同时有相反方向的MCP集成：`mcp_server`让外部AI访问HA，MCP Client让HA自己的Agent调用外部工具。Home Mate访问HA时的角色与前者对应，不能装反后靠补丁修方向。

MCP的resources/prompts不自动变成有副作用的工具；外部描述和内容是数据，不是更高权限指令。模型厂商的function/tool-calling格式由模型适配层转换，不能直接替代项目工具合同。

Home Mate未来也可通过MCP Server对外提供受限工具，但属于另一角色和范围，不能因支持MCP客户端就自动开放管理权限。MCP不作为PCM/视频持续媒体传输的默认设备协议。

### 家庭音乐服务与后台配置

Home Mate 通过工具接口使用可选音源。家庭部署可让旧 RUI 与 Home Mate 分别作为客户端，调用同一套 Personal Services。Home Mate 按 HTTP 接口对接 `music-svc`，需要笑话服务时可沿用同一方式对接 `joke-svc`。旧 `rui-private-source` 是 RUI 进程内的插件，仅供迁移时参考。商用产品交付通用接口和适配代码，家庭私仓的音源解析实现按照其自用范围独立部署。

| 配置归属 | 用户可以管理的内容 |
|---|---|
| Home Mate 后台「工具 → 音乐」 | 启用在线音源，设置 Personal Services 地址与客户端连接凭证，分别测试搜索、取流。独立启用 Navidrome，设置连接信息和音源搜索顺序。页面展示各来源的实际状态、错误及最近入库结果。 |
| Home Mate 播放与入库 | 每个房间的队列、暂停、停止与播放历史由底座维护。页面可独立开关自动入库，选择部署时已授权的目录。家庭部署沿用在线歌曲实际向目标设备发送音频后自动保存的偏好，按来源和曲目去重。搜索、预取、连接测试均不触发入库。 |
| Personal Services 自己的配置 | 维护上游音源密钥、代理、解析实现及批量下载节点。继续使用该服务现有配置方式。批量采集工具用于显式发起的曲库整理任务。首版日常操作统一使用 Home Mate 音乐页。 |
| Navidrome 自己的后台 | 用户、曲库索引和个人播放器由 Navidrome 管理。Home Mate 接入时配置专用普通账号，默认只查询和取流。Web 或手机客户端的队列、历史与收藏由对应客户端和账号管理。 |

客户端连接凭证保存在 Home Mate 的受保护配置中，回读只显示配置状态。上游密钥只由 Personal Services 管理。关闭或未配置 Navidrome 时，已启用的在线搜索、播放与归档仍可工作。家庭 NAS 的“音箱点播”是一个可选归档目的地，Navidrome 可自行索引该目录。

## 3. 工具合同要定义什么

首批接口草案应明确下列语义，具体字段按必要范围设计：

- 稳定名称/命名空间、版本、来源、能力说明、输入与输出schema。
- 查询或改变状态、目标/家庭/房间/资源范围、授权要求、并发资源约束。
- 候选与事实的来源、媒体类型、匹配条件，不让工具私自替换用户目标。
- 请求与任务关联、超时、取消可达边界、幂等/重试条件、重复请求处理。
- 状态与结果证据：已接受、处理中、已完成、失败、部分完成或未知分别表达；业务完成和网络成功分开。
- 长任务的进度、回执/状态查询和结束规则。取消不等于撤销已完成动作，不确定写操作不盲重试。
- 能力动态变更、不可用、限流、缺凭证与协议不兼容的可诊断返回。

实际授权由底座执行层核对。MCP工具注解、模型声明或第三方工具描述均不能自己授予权限；普通API、本地工具与MCP适配都经过共同执行边界。

HA首批仍保持已约定的灯/窗帘开关范围；通用工具接口不自动扩大可操作实体或动作。精确实体ID和授权范围来自实际接入配置，不让模型编造。

## 4. 四类接口要分清

| 接口 | 使用者与主要用途 | 设计要求 |
|---|---|---|
| 助手服务接口 | 页面、APP、自动化或第三方客户端提交文本/附件并消费回应 | 会话/任务身份、流式结果、取消、错误、输入类型与模型能力；无需音箱 |
| 管理接口 | 用户页面、获授权的语音管理、开发Agent | 共同配置校验/生效/历史/诊断，权限不随普通聊天请求自动获得 |
| 设备与媒体接口 | 外部Dot桥、未来板子/摄像头适配组件 | 能力、协商、连接代、命令/事件、媒体生命周期与实际回执；延续设备桥边界 |
| 工具/扩展接口 | 原生服务、MCP适配和第三方业务插件 | 工具合同、登记、授权与结果映射，不依赖核心内部对象 |

这些接口可以共享身份、错误和事件基础定义，但不强制共享同一连接或传输协议。管理HTTP接口优先评估OpenAPI描述；事件、设备及媒体传输分别做适用性验证。MCP选用的协议版本、传输与Rust SDK需固定并兼容验证，不能假定最新文档和所选SDK一致。

后续补齐认证、授权范围、会话/家庭与设备数据隔离、版本兼容、弃用和可观测性。是否本地单家庭、多家庭托管或商业设备套装仍待明确，不提前建设完整多租户云平台，也不能用一个全局状态假定永远只有一户。

## 5. 自有契约的拟定方法

1. 从文本请求、Dot语音、无扬声器ESP32事件和摄像头取图几个用例提取共同语义，标明首期实现与未来能力。
2. 定义消息/媒体类型、身份与范围、动作和结果状态、超时/取消/重连/重试规则，再选择传输。
3. 用可机读schema、请求/响应示例、事件次序和错误示例表达合同；给出能力不支持与未知结果的处理。
4. 将产品版本、设备协议版本、API版本和工具schema版本分开；新增可选能力和不兼容变化的规则明确。
5. 用客户端/虚拟终端与独立桥测试端验证，再冻结首个可用版本。不能只凭文档外形漂亮或JSON能解析通过。
6. 规范/SDK的公开授权方式按[商业许可规划](commercial-licensing.md)决定，不把API契约当软件LICENSE或客户服务条款。

## 6. 指导第三方开发的最小材料

在正式对外邀请开发或交付SDK前，需要具备以下材料；当前仅规划，不生成空壳SDK或宣称已支持：

- 角色、连接方式、版本兼容、能力模型及权限说明。
- 可机读schema与按场景组织的文档，正常/失败/取消/重连序列和参考消息。
- 最小文本客户端、一个虚拟设备、一个只读工具的示例；音频/图像适配示例按实际能力提供。
- 本地测试端与共用合同测试：没有真实硬件也能开发工具/桥；核心没有品牌库也能测试。
- SDK是否必要、支持哪些语言与版本、如何注册/配置/查看实际状态；不强制外部开发者使用Rust或安装核心内部开发环境。
- 变更日志、兼容期/弃用规则、错误定位、报告问题所需最小脱敏信息，以及SDK/示例许可。

建议先交付可直接使用的协议与示例，再依据实际接入困难决定SDK范围。内部重构不应迫使第三方同步改代码；共同新能力按规范版本演进。

## 7. 后续调研与验收安排

- **N0.1**：明确商用形态、首批助手/管理/工具用例和能力模型；明确HA路径需要的实体/动作/回执，拟首批合同。
- **N1**：核对MCP规范与Rust SDK支持版本、许可、取消/错误与工具发现；比较HA原生与MCP映射，不默认双接。内核候选也检查能否接入自有工具合同。
- **N2**：真实接口打通页面与服务，并验证无音箱的文本请求路径；工具调用仍经统一执行边界。
- **N3**：用虚拟图像/板子事件验证可选能力和媒体来源，结合首期范围决定是否接真实视觉引擎；提供第一组合同示例和开发指导。
- **对外商业交付前**：按实际承诺能力完成兼容/合同/权限与依赖许可复核，不能把可扩展设计写成已支持全部ESP32板或摄像头型号。

本轮交付的是关系梳理、通用接口方向和具体调研任务；尚无可调用API、MCP适配、视觉能力、SDK或开发者认证体系。
