## 1. 这个项目现在的样子（事实，不是目标）

一台 Echo Dot 2（dot2-d）上跑着完整链路：唤醒 → 云端 ASR → 云端 LLM（双供应商兜底）→
云端 TTS 流式 → 音箱播放；播放中说关键词（实测 P50 300 ms 停播）或直接说话（检测 160–240 ms）
都能打断；控制台能看能改全部语音参数；固件和核心都能经管理 API 自更新（A/B 两槽）。
主仓 135 条测试、网关仓 109 条，跑过一次 185 分钟长跑。

所以"从零写"更接近**重做实现、沿用结论**，而不是从第一性原理再推演一遍。

## 3. 平台事实（这些我是撞出来的，重推一遍代价不小）

- **CPU 与内存**：MT8163 四核，但 MTK HPS 稳态只留 1 核在线（体温 37–40 ℃，不是过热）；
  停掉 HPS 四核全开时全机 busy 只有 9.4%。总内存 471 MB，可用约 426 MB。
- **`/run` 只有 4 MB tmpfs**：我的一次环回探针把三条 960 KB 的轨道写进去，加上日志就满了，
  固件随后 `exit 101`，连 panic 文本都写不出来——因为 stderr 也落在同一个 tmpfs 上。
- **emOS 没有 Android 用户态**：没有 adbd（串口是唯一通道）；没有 HAL（codec 的 DAPM 路由
  由固件自己发 ioctl 拉起来，10 条路由＋amp 时序）；WiFi 由 init 拥有（`wpa_supplicant` 是
  `/init` 的子进程，`kill` 后约 1 秒重生，`stop <svc>` 在这个 init 上没有效果）。
- **armv7 我用的目标是 `armv7-unknown-linux-musleabihf`，构建走 `cargo zigbuild`**。有一次
  配方写成 `musleabi`，编译没报错，跑起来只有 4.7 chunks/s（正常 12.5）——是"整体慢下来"，
  不是局部报错。后来我把 `chunks_per_sec ≥ 12` 当实时哨兵，上机第一眼看它。
- **内核是 3.18**，AArch32 的 compat 表里没有 `clock_gettime64`(403)、`statx`(397/291)、
  `rseq`(293)。走错一步的链子：每次调用 → MTK `traps` 打 24 行寄存器 dump → 写
  `console=ttyMT0` 时 console 驱动关中断 → 音频 SPI 100 ms 传输超时 → 厂商 `spi_data_read`
  空指针 → 内核死 → `wdt_by_pass_pwk` 整机复位。我最后把时间调用改走 32 位 263、
  `Path::exists()` 改 `access(2)`、核心的 `fs::metadata` 改 open/lseek/read，才止住。
  `console_loglevel=0` 我当时没采用，因为它会连 `last_kmsg` 的现场一起静音。
- **AEC 我放在了设备上**（7 路 speex + 33 抽头融合 + ch8 环回参考）：tail 2560、
  ERLE 中位 22.8 dB、盲窗 200 ms、单核 CPU 35%。这几个数字是我冻结的标定基线，改任何一项
  我都按 `docs/d/t8-echo-20261109.md` 的方法重量过一次。

## 4. 我用的验收判据，以及为什么是这种形式

这几条是踩坑之后才改成的，附上当时的反例，你可以判断是否沿用：

- **打断**：一次说话 → 恰好 1 次停播 → 1 个完整段 → 1 次一致 ASR → 回答播完 → 之后 10 秒
  零新停。反例：我第一版用"`barge.stops` 增量 > 0"判成功，而实现当时正在自激循环里反复打断
  自己，3 轮把计数刷到 17，脚本报了"3/3 通过、P50 120 ms"，用户当场否掉。计数型判据会被
  自激喂成绿色。
- **自听**：播放中自听段 = 0；另外"没人说话时不可能造出一句话"（我把打断前滚只留档、不回灌
  ASR）。反例：回灌之后 ASR 把设备自己刚说的话转写回来，核心当成新指令回答，用户听到的是
  "自问自答"。
- **复位**：看 `/proc/uptime` 的连续性和 trap 的 **age**，不看计数。反例：64 KB 环形缓冲饱和
  后 `grep -c` 会从 96 掉到 90 再掉到 89，看起来像"好了"，其实只是被挤出去。
- **交付**：每个用户能碰到的能力，我当时要求自己能回答"控制台哪里能看到/改到"。
  `barge_protect_ms` 在 T5 落地时就支持 PUT，但页面上只有显示、没有编辑器，是收尾时才补的滑块。

## 5. 两个我到最后也没解决的问题

**① 固件约每小时被内核 OOM 杀死（我留下的唯一发布阻塞项）。**
症状：RSS 5.7 MB → 约 270 MB，监督器 `exit code=137`，57/61/63 分钟各一次。
四刀二分：断掉北向（无上行、无播放）→ RSS 三分钟恒定 1,008 kB；关 AEC → 速率不变；关近端
检测 → 速率不变；275 ms 片段 +0.1 MB/次 vs 28 s 片段 +7.9 MB/次 → 与**播放时长**成正比。
然后装了一个记账全局分配器（每播放结束打印 `live = allocated − freed`）：**`live` 每次回到
0.41 MB，而 RSS 同期从 6.0 涨到 11.0 MB**。所以这一版**程序没有逻辑泄漏**，是 musl 对
"整段 WAV 播放"路径上 2.7–5.4 MB 大块的保留/碎片化。
我当时列的三个方向（你可能有别的）：
- 换全局分配器（mimalloc 是 MIT，走你们的依赖登记流程）；
- 把整段播放的大缓冲做成可复用池；
- 让设备端不存在"整段音频"这条路：核心只发流式 chunk（PlayBegin/Chunk/End），设备端永远
  按 period 消费，任何时刻不持有 MB 级缓冲。这条我个人觉得从架构上最干净，因为我这一版的
  问题恰好出在"整段播放"这条旁路上。

**② 近端检测偶发误触发（无人在说话却停播）。**
实测：真实的摄像头刺激能量在 −27.6…−30.3 dBFS；唯一的误触发在 −42.4 dBFS。看起来抬高门限
就能滤掉，我把 `--barge-in-db` 从 −45 提到 −38 试了一次：同一轮刺激反而出现 2 次停播、ASR
多了一段「哦。」，首个误触发仍然落在刺激**之前**（`corr=0.186 energy=−31.9 ref=−13.5`
——参考很响时残余的能量也不低）。所以绝对能量门限对这类样本无效，我把标定退回了真人验收过的
−45。方向我觉得是加"相对参考电平"（`energy − ref`）这类判据，或加长确认窗——这两条我都没验证。

## 6. 方法上哪些做法帮我省了时间（反例都附上）

- **把判据写进工具**，让工具输出 PASS/FAIL 和失败条件，而不是我去读日志。`t5_bargein_verify.py`
  就是按这个重写的。
- **仪表默认零稳态开销、随时能关**。反例：环回探针常开时 chunks/s 掉到 8.8–11.3。
- **先复现再修**：让旧代码稳定失败、保留失败断言，再用同一个测试转绿。概率压测我算作没复现。
- **A/B 固定预热，或者交叉**。反例：固件重启后第一个 56 s 天然带误触发（实测 11 与 15 次），
  我第一版 A/B 的四组条件顺序恰好就是预热顺序，得出了"音量越低越安全"的错误结论；加 2 遍
  预热后同一条件是 0/0/0。
- **延迟类指标先把口径钉死**：同一批数据在"段内峰值 −12/−16/−20 dB"三种门限下分别是
  300/290/80 ms。
- **跨层 shell 里避开精细引号**：`bash → serial_cmd.py → tty → mksh` 四层转义之后
  `grep 'keyword\":'` 收到的模式带了字面反斜杠，永不匹配，我一下午都在冤枉被测物。
- **测量脚本自己的时钟假设也会造假**：设备无 NTP，核心时钟比 Mac 慢 42.6 s，长跑脚本用
  Mac 时间戳开窗，于是多出 9 个"幻影误触发"；改用核心自己的事件游标后消失。
- **刺激源尽量与设备同位**（我用摄像头外放）；唤醒类测试我保持 ≥35 s 间隔，因为 30 s 跟随窗
  会把后续唤醒算成 followup_turns，看起来像"灵敏度退化"。
- **需要人在场的几项**：LED 逐灯目视、音量键手感、跟随窗提示音听感、真人唤醒率、真人打断、
  音乐浸润。这几项我这一版一直标"未验"，没有拿自动化结果冒充。

## 7. 如果重来，我倾向的顺序（个人偏好）

三边界与协议版本先定（大脑 / 设备网关 / 工具插座；协议是两仓唯一耦合面）→ 先跑通文本回路
（模型＋工具＋取消＋trace；我这一版 80% 的语音调试时间花在时序而不是语义）→ 尽早让设备
"可观测"（开机哨兵、诊断端点、串口全通道、A/B 槽；P0 那种事故如果没有这些会烧掉一周）→
AEC 在真机标定并冻结（ERLE→冻结→CPU→VAD；我试过顺序颠倒，等于全部重测）→ 打断分两层
（设备侧反射 300 ms ＋ 核心语义 160–240 ms）→ 长跑放在所有音频改动之后（我排了三次才真跑成）。
