## 一、已经达成的方向

1. **独立从零设计。** 新项目采用清晰的边界和接口，不继承旧项目的目录、补丁链、隐式状态与框架选择。
2. **迁移知识资产。** 设备协议/能力、房间参数、调试结论、失败实验、历史录音和验收场景有条件迁移。参数连同固件、信号路径、验证方式及可信程度保存，不复制未经验证的结论。
3. **一个大脑＋一个底座＋两类插座。** 大脑直接与用户对话并统一组织目标、上下文、规划与纠错；底座可靠执行并报告事实；硬件插座接语音终端，工具插座接应用能力。底座仍检查权限、范围、任务有效性和取消。
4. **核心采用模块化单体，设备网关独立新工程。** Home Mate核心一个主服务，按职责划分模块；硬件工程正式名为Home Mate Device Gateway，简称设备网关。接手Agent新建私有仓库`yes999zc/home-mate-device-gateway-b`从零开发，通过版本化协议独立接入、维护、测试和发布；旧桥只读参考，不续写、整仓复制或作为运行依赖。网关可与底座同机运行；内部音频/推理隔离按需求决定。建仓与首批任务见[工程交接](device-gateway-project.md)，当前尚未建仓。
5. **Rust为核心服务首选。** 核对目标NAS及关键引擎依赖后最终确认。大脑可直接用Rust调用LLM；需要Python的引擎可独立适配，不默认维护两套中枢。语言不保证无业务错误，也不能替代音频算法与声学验证。
6. **Vue＋TypeScript管理页面，Rust管理接口。** 前端语言与后台服务语言分别选取；页面围绕大脑、设备、工具和运行事实组织。视觉方案尚未确定。
7. **请求按需要投入计算。** 明确且唯一的小动作可快速执行；普通语义请求可一次模型调用选工具；多步骤目标才进入持续规划。快路径共享同一执行和结果记录，不能膨胀成关键词语义系统。
8. **可维护和可演进优先。** 替换模型、增加硬件和工具应集中在相应边界。每种状态与决定有明确归属，公开接口隔离内部实现，新机制替代旧机制时安排后者退出。
9. **硬件知识由桥吸收。** 设备协议、固件差异、原始布局、音量映射及硬件操作留在桥；底座保留通用语音终端抽象、任务与交互管线。AEC可采用mic＋ref或已处理语音合同，实际所有者必须明确；首期形式与位置待验证。新共同能力通过接口版本演进。
10. **首期实机硬件只有 dot2-d。** 2026-11-07用户决定取消四房推广，部署顺序改为单房后直接评估音箱内同内核；dot2/dot2-b/dot2-c不再属于首期范围（其基线证据保留作参考）。dot2-d已由用户分配为本项目测试音箱，经USB连接开发机。LX06后置，不列入首期实现或验收。设备快照见 [Dot设备基线](dot-device-baseline.md)。

11. **管理页面随功能交付。** 用户能独立做常用配置、状态查看和排查；最小完整链路包含真实管理API与相关页面。页面显示配置来源及保存/实际应用/失败/未确认状态，Agent日常配置也走同一接口。
12. **分阶段设计、验证和评审。** 先明确首批需求与初步架构，再用技术验证确认选择；接口、实现、页面和测试按功能批次一起推进，重要批次独立评审，复用未失效验证。

13. **Agent内核Rust优先，借鉴成熟方法。** 调查Rust原生组件与最小实现，不限定Pi，也不默认全部自研。仅为复用内核不默认新增跨语言运行时；模型客户端、循环、会话与家庭任务分别评估，组件须可替换。

14. **家庭伙伴支持双工协作与语音管理。** 从首期架构支持全双工，日常默认半双工，通过语音切换；换音色、适合开放的参数和简单诊断通过共同管理能力完成。双工能力、对话参与和主动发言分开；语音和页面共享真实生效状态。

15. **从初期考虑商用许可。** 内核、SDK、模型/音色、原生库与分发资产选型核对具体版本及依赖许可；自有代码/接口规范/SDK授权与客户条款分别决定，不自动给核心加开源许可证。
16. **通用服务与能力接入。** 大脑与任务接口可被无音箱客户端使用，设备按可选能力接入；为ESP32、摄像头/图像和纯文本留合同与测试场景，首期实机只有 dot2-d（四房已取消）。视觉需模型/引擎实际支持，不把规划当已支持硬件清单。
17. **工具合同独立于接入协议。** Home Mate拥有统一工具执行边界；MCP是外部能力适配协议，HA是家居能力后端。原生API/MCP等适配映射到同一合同，不默认重复暴露或扩大权限。对外接口须有版本、示例、错误说明与合同验证。

18. **家庭音乐服务可选接入。** 在线音源、Navidrome 曲库和在线歌曲自动入库分别配置。日常配置与诊断进入 Home Mate「工具 → 音乐」，Personal Services 独立管理上游与采集配置。详细分工见[工具层规划](interfaces-and-tool-layer.md)。

## 二、职责边界

| 模块 | 核心职责 |
|---|---|
| 大脑 | 理解意图，维护目标和约束，结合上下文选择动作，根据结果与用户纠正调整 |
| 任务运行器 | 管理任务身份、状态、暂停、插问、替换、取消与执行协调 |
| 通用音频系统 | 接收合同音频与实际处理状态，管理通用唤醒/识别/播放管线；需要时使用通用AEC，硬件原始处理由桥封装 |
| 设备/媒体接口 | 按可选能力接入语音、文本/事件、图像等，核心无音箱也可工作；外部品牌桥封装硬件差异，提供实际状态 |
| 统一工具层与适配 | 定义能力、授权、任务与结果合同；HA原生、MCP和其他适配接入共同执行边界，不私自替换目标 |
| 管理接口 | 向页面提供配置、状态、操作接口，不重复维护业务状态 |
| 存储与配置 | 保存事实、偏好和分层参数，负责校验、来源与格式迁移 |

核心内部这些职责不强制一项一个进程、一个包或一个文件；设备桥已经明确为外部独立组件。Rust的module/crate边界及目录在设计时确定；代码长度仅作检查线索，不是架构验收标准。

## 三、部署路线与工程里程碑

以下是产品部署顺序。当前授权覆盖本地和隔离开发，真实家庭设备试用另按 [HANDOFF](HANDOFF.md) 的范围执行。

| 产品阶段 | 运行位置与范围 | 验收依据 |
|---|---|---|
| 一 · NAS 内核，单房对话 | Agent 内核、任务运行器和控制台以 NAS 为目标（当前测试机为荣耀NAS，见[HANDOFF](HANDOFF.md)）。先用文本、虚拟终端和假工具开发，实机为 dot2-d，通过独立设备网关接入。 | 一轮故事能接受“换个短一点的”并保持语境。点热榜时能按需要查榜、找歌、播放，遇到失败能改选或说明。可取消，控制台可查实际结果。记录模拟与单台实测各自覆盖了什么。 |
| 二 · 可选的音箱独立运行研究 | 在 dot2-d 试验同一套内核作为开机自启程序，通过网关接口收放音。沿用相同的外部服务。到实测时再决定是否建短期实验分支。 | 在隔离环境切断通往 NAS 端 Home Mate 内核、网关和音频处理（含 AEC）的路径，保持所选外部服务可达，验证单台能完成一轮语音交互。若仍依赖 NAS 上的网关或音频处理，仅记录内核移植结果。随后对比首声延迟、CPU/内存余量、播放中回声、轻声识别、持续运行与升级恢复。根据实测收益决定是否推广。 |

### 已知风险（跨里程碑跟踪）

- **硬浮点 ABI 锁定＝全局约束（2026-11-08 G6 收口轮由风险升格为规则）**：所有 armv7 构建与 native 依赖（speexdsp、将来的 opus、任何 C 库）一律 `armv7-unknown-linux-musleabihf`，且必须同一套 hf 工具链编译（构建命令＝`cargo zigbuild --target armv7-unknown-linux-musleabihf --release`）。`musleabi` 只许纯整数场景；改回软浮点三元组＝事故（编译不报错、只是整体变慢——本轮实测 38% 实时率，是跑不动不是慢一点；混入单个软浮点库同样无声）。哨兵＝上机第一查 chunks_per_sec≥12（已写入网关仓部署记录与验收 §0）。`eabi` 后缀出现在任何音频/DSP 链路的构建配方里都应视为红旗。

D1 中语音形态先做到事件级仿真（唤醒事件、文本输入、播放回执、音频落盘），真实 ASR/TTS 服务由用户选定后即插；dot2-d 实机接入在 M2 之后按 G2 推进。

[HANDOFF 第 5 节](HANDOFF.md) 收录讨论中的使用场景和回归案例，供相应里程碑选择。

不把“编译通过”当作功能完成，不把连接在线当作声学验收。复用历史证据，不默认重做长时间真人陪测。
