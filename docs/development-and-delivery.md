## 2. 开发顺序与阶段出口

以下 N0–N4 是工程步骤。按[产品部署路线](plan.md#三部署路线与工程里程碑)，单房和四房先后验收，设备端内核研究可选。需求、架构、技术选择和验证允许迭代，先提出足够清晰的设计，验证关键假设，再依据证据调整，不等写完全部功能才接设备或页面。

| 阶段 | 工作与交付 | 本阶段出口 |
|---|---|---|
| N0.1 首批需求与设计 | 从真实使用场景选首批范围；明确职责、任务状态、双工/参与规则、首批接口草案、语音及页面管理操作与验收；指出关键风险 | 实现者与评审者能据此说明“做什么、怎么验证、还不知道什么” |
| N1 关键技术验证 | 按迁移指南核对设备/参数；用虚拟终端和测试端验证版本化设备合同，验证Rust、外部Dot桥与关键引擎接缝 | 关键接口和目标环境可行；依赖、音频时间轴、并发收放音/参考与模式切换、停止/重连及未知项有记录；据此确认或调整技术选择 |
| N2 最小完整链路 | 管理页面配置→管理API→核心服务→语音/模型/一个查询与一个执行工具→桥/虚拟设备→结果与页面记录；包括语音模式切换与实际状态，覆盖取消和失败 | 真实接口下完整可用，用户看得到配置和结果，不依赖开发脚本维持日常使用 |
| N3 按功能批次扩展与迁移 | 每批共同交付核心逻辑、接口、相关管理页面、迁移资产与验证；逐步覆盖多轮和四房场景 | 本批目标、异常路径及相关旧经验验证完成；未测声学保持未知 |
| N4 单台试用到四台 | 后续授权范围内执行，保留旧RUI日常服务和适用恢复材料 | 具体行为、管理操作和运行证据达标后再推广，不以在线替代验收 |

N1中彼此独立的硬件/音频验证与文本模型实验可以分别推进，但共享首批接口假设，并尽早合成验证。不能让桥、核心和页面长期各做一套再在最后整合。

首批已允许必要的小规模DeepSeek验证，仅连接假工具/假设备；本地依赖安装与实现按HANDOFF执行。实体音箱接管、旧RUI操作及生产部署不在本次范围，不能为验证而改动日常系统。

## 3. 一批功能怎样完成

一批应围绕一个可用行为，而非单独交付全部“前端层”或“后端层”。例如“修改指定房间音量”包括：

1. 明确目标设备、音量语义、限制、不支持和失败返回。
2. 页面显示当前值、来源、待修改值与影响范围。
3. 管理API校验，按定义保存并请求桥应用；桥验证物理限制。
4. 页面区分已保存、等待应用、实际生效、失败或未确认。
5. 查询或重启后的行为符合该配置的保存与恢复规则。
6. 关联测试与结果记录可以追溯本次请求，不把旧回执当新成功。

真实接口和本批必要页面没有完成时，可标记“核心接口已完成”，不得标记“功能已交付用户”。不要求给每个内部算法单独做页面；常用操作与高级诊断分别设计。

## 4. 管理页面是产品能力

术语：**管理页面**是用户在浏览器操作的Vue＋TypeScript界面；**管理API/核心服务**是Rust服务。两者从早期配合实现。

**同步推进规则（2026-11-07 用户立规，G3 教训）**：控制台不是"事后补的皮"，与本批代码同一里程碑交付。每个 user-facing 功能合入时，其管理 API 与必要页面必须同批落地（模拟界面不算集成交付，见 §5）；里程碑收尾的 big picture 核验要逐项回答"这个新能力控制台哪里能看到/改到"，答不上来就是欠账。功能后端先行验证、UI 紧随同批合入是允许的节奏，但**跨里程碑未补即违规**，须在 HANDOFF 明示为未竟项并排入下一里程碑首项。

已达成的要求：用户能自行完成常见配置、状态查看和排查，避免每次依赖Agent改文件。至少覆盖本批已提供能力的：

- ASR、TTS、LLM 各自选择服务及连接配置，分别展示连接验证与生效结果。以替换其中一项、另外两项仍按原配置工作作为验收场景。
- 工具常用设置、设备与房间配置、必要的任务操作；具体字段随首期范围定义。
- 当前有效值、默认/型号/房间覆盖等来源，区分可编辑、只读和桥不支持项。
- 变更影响哪台设备、是否需重启或重新连接，不能保存后才隐性改变全屋。
- 已保存与已实际应用的区别，以及失败/未确认原因。
- 近期变更记录与适用配置恢复；恢复不能覆盖无关新编辑或盲目重放设备动作。
- 本次识别文本、用户目标摘要、执行动作、结果与阶段耗时；缺失证据明确标示，不暴露凭证或模型内部思考。
- 已有设备能力与桥配置描述通过通用接口呈现，不写Dot专属业务分支。

凭证输入/展示规则随接口设计明确；不能通过读取或显示整份运行配置来实现管理功能。核心UI按工作区约定提供简体中文与英文。

用户语音与Agent日后修改日常配置应使用同一管理API，经过同样校验、应用与变更记录。配置文件可作为启动/备份形式，但不能形成另一个绕过实际状态和审计的日常修改入口。

### 用户可以输入和修改什么

在设计某项功能的管理 API 和表单前，先用一句话描述用户任务。对每个拟开放的设置，说明谁会在什么情况下修改它、哪些输入有效、影响哪台设备或哪个家庭，以及用户如何验证结果。遇到影响日常使用而尚未明确的偏好，用一个具体操作示例与用户沟通。各功能在进入对应里程碑时细化这些决定。

日常页面提供完成该任务所需的输入和操作。只读状态用于解释当前效果；有明确维护用途的调节项放在高级设置或诊断页。仅供程序使用的内部参数留在实现层。管理 API 显式声明允许修改的字段及校验规则，页面和语音管理共同遵守。后端增加内部配置项时，用户表单和可写 API 字段都应由产品用途决定。

例如，若天气工具支持默认城市，验收可以让用户在页面把默认城市改为杭州，保存后问“明天会下雨吗”，核对查询使用的城市；再问“北京呢”，核对临时查询是否按约定保留默认城市。城市无效或服务不可用时应能看到原因。城市、服务商等具体可配置项由该功能设计确定。连接重试次数等实现细节仅在有明确排障用途时进入诊断界面。

## 5. 前后端协作

1. 先约定本批助手与管理HTTP接口，可采用OpenAPI或等价的明确schema；设备流协议和工具接口分别定义，不强行把所有流量都装进HTTP请求。
2. 共同确认字段语义、单位、缺省、错误、未知状态和异步操作身份，而非只约定JSON外形。
3. 页面可使用遵循合同的模拟服务先实现交互；服务端按同一合同实现。生成客户端/类型如确有收益可采用，不预先绑定生成工具。
4. 本批早期即连接真实接口，验证实际配置、异步状态、失败和刷新/重连；模拟界面不算集成交付。
5. 页面和API共享事实来源。修改接口时同步消费端与合同检查；桥或工具的硬件/业务状态由对应所有者报告，不在页面重新推断。

第一批不追求完整后台的所有页面或最终视觉，但必须具备本批操作所需的可用界面。

## 6. 审核与测试闸口

按改动风险与阶段执行，不给每个小改动重建整套验收。

| 闸口 | 内容 | 时机与通过依据 |
|---|---|---|
| 设计检查 | 职责、依赖、事实/状态所有者、接口、错误/取消、管理入口 | 新接口/跨模块行为编码前；范围和验收清楚，未知项已标出 |
| 自动检查 | 编译、类型、适用的静态检查、受影响单元/合同/集成测试 | 相关代码批次合入前；关键受影响检查通过，失败有明确归属，不能改口称通过 |
| 独立代码评审 | 对照目标检查实际差异，重点看边界、并发、迟到、失败、泄漏和重复机制 | 有意义功能批次与接口改动；由未实现该批代码的Agent评审，问题修复后定向复核 |
| 阶段验收 | 实际构建产物、管理页面、模型/桥/音频组合，按场景操作与故障注入 | N1/N2/N3/N4对应阶段；证据可复查，模拟/安装/设备/声学分开 |

常规批次可采用一名实现者加一名独立评审者，测试由实现者执行并提交证据；高风险音频、协议和取消边界增加独立验证。应独立评审的批次可先提交实现；缺少独立评审时状态为“待独立评审”，完成评审并处理相关问题后再标记验收通过。

自动检查后续在仓库中落实为持续集成。Rust、页面和协议各运行受影响检查；未接入相关实现的文档改动只做文档与链接核对。不为当前文档阶段创建空测试体系。

已通过结果仅在相关代码、接口、依赖、配置、路径或新失败使其失效时重开。旧测试的断言若绑定旧实现，提取行为再改写，不能为通过测试保留旧缺陷。

真实模型验证与确定性执行测试分开：模型场景检查意图改写、约束保持、纠错和必要工具选择；执行测试检查授权、取消、证据等级和房间隔离。记录使用的模型/配置、输入、重复次数、失败和耗时；不能仅凭一次成功或固定文本匹配宣告智能达标。

对外SDK/接口交付增加合同示例、兼容和独立接入验证；商业发布按实际产物复核许可与声明，不能把根README许可初筛当完整发行结论。

不在每次提交上自动发起付费模型或实体设备测试。计划中明确触发范围与预算；历史录音和模拟优先复用，不新增真人陪测门槛。

## 7. 技术与设计风险如何处理

- **为复用Agent框架增加更多状态与运行时**：先分清模型客户端、循环和家庭任务职责；优先Rust原生候选或最小实现，组件可替换，不照搬完整编程Agent。
- **为了全Rust重写成熟引擎**：先核对接入和运行代价，复用成熟算法；外部调用的阻塞/异常隔离要验证。
- **接口分仓但实现仍耦合**：使用独立桥合同测试端；底座不导入品牌实现与桥内部配置对象。
- **把大脑又做成固定分类器**：目标与任务状态作为共同上下文，验收未参与实现的改写和跨场景修正；不逐句补运行时分支。
- **为通用性建设过多抽象**：首批只实现完整链路需要的接口和边界；新增层说明当前用途，避免先建设未来插件市场或微服务体系。
- **持久化状态造成重复动作**：明确配置、偏好、事实、活动任务的保存语义；重启不等于允许重试所有未确认操作。
- **将全双工等同全天参与**：分开音频能力、会话和主动发言，默认半双工；语音设置与模式状态实际生效可核对，不能只改模型话术。
- **换音色但保留错误ACK模板**：将TTS音色变化与提示音参考/时序保护一起验证。
- **只重视模型回答，忽略底座时序**：音频与取消不等待模型及时返回；按阶段观测延迟、积压与执行状态。
- **可用性被拖到收尾**：管理页面、配置生效反馈和排查能力从N2开始随功能验收。

## 8. 开工前最小交接内容

接手Agent应先把以下首批内容写到现有规划或对应合同中；无需再复制一套项目管理文档：

1. 本批用户场景、明确边界、失败/歧义处理及完成条件。
2. 相关模块、状态所有者、请求/事件与版本兼容草案。
3. 要验证的技术假设、环境、材料、预期证据与待定项。
4. 本批管理操作、配置应用/重启规则、保存/恢复范围。
5. 受影响测试、独立评审范围、模型/设备调用范围及阶段验收办法。
6. 本批引入依赖/模型/素材的许可依据、第三方接入的版本与示例，以及无音箱可选能力检查范围。

有足够信息时直接推进已授权工作；只有需要用户偏好、改变既定范围或缺少必要授权时再确认。用户已明确要求接手即可开发，按HANDOFF开始实际隔离实现，不再等待重复的编程启动确认。

交接时状态：流程与管理交付要求已入规划，已授权首批必要设计与隔离代码；schema、依赖和实现仍需接手完成，实际进度更新HANDOFF。
