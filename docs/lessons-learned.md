# Lessons Learned（踩坑记录）

目的：把每个大节点**实际踩过的坑**按"现象→根因→修复→预防"固化，供后续里程碑与后续接手者直接引用；只记真实发生过的事，不记猜测。日期均为 2026-11-07（M0–M3 同日完成，坑的发现顺序按里程碑）。产品决定与路线图不入本文件（归 [plan](plan.md)）。

## 横切铁律（多条坑的公共根因，最先读）

1. **四个"完成"时点绝不能混用**：模型答完 ≠ 合成完 ≠ 网关收到播放命令 ≠ 音箱实际播出。任何"完成/停止/取消"逻辑必须先问自己在说哪一个时点。（M2 喊停竞态的根因。）
2. **先稳定复现，再最小修复，同一测试证明**：时序问题用可控同步点（门控假件、async 一次性钩子）让旧代码稳定失败，保留失败断言输出；概率压测不算复现。（M2/M3 竞态方法。）
3. **验收走用户真实入口，证据看下游命令**：语音/按键/控制台各自只算各自的证据；证明"只播一次"要收集到该轮结束统计全部播放命令，内部日志不能冒充设备行为。（M2/M3。）
4. **静默死亡是最危险的失败形态**：spawn 的任务里 panic 会无声消失，任务/trace 永远"运行中"。所有退出路径必须收尾；字符串截断等可 panic 点要专项检查。（M1 错误收尾＋M3 UTF-8 截断。）
5. **确定性测试证明合同，不证明模型**：循环/工具/取消的合同用假模型钉死；真实模型的行为（会不会跳过工具、会不会编造）只能靠真模型场景脚本，换模型必复跑。（M3 真模型缺陷。）

## M0 建仓（无重大坑）

- 习惯固化：**新私仓建立后必须在 Web 界面人工核实 PRIVATE 与推送权限**，不能只信创建命令返回（本轮已核实，写下来防止下次省略）。

## M1 大脑最小回路

1. **工具名 wire 映射**：内部点号名（`music.play`）不符合 OpenAI function-name 字符集（只许 `[a-zA-Z0-9_-]`），上线即"工具查无此名"。→ wire 层统一转下划线、回程统一恢复点号（`to/from_wire_tool_name`），两侧各配测试。预防：内部命名与 wire 命名永远分离，映射函数是唯一通道。
2. **tool_calls 流式拼接**：兼容端点的工具参数在增量流中分片到达且 arguments 是字符串化 JSON，整段拼完才能解析。→ 按 wire 原样累积，结束时统一解析；解析失败以 `_parse_error` 原文入上下文，不静默丢弃。
3. **错误路径不收尾**：运行时错误（存储失败等）直接 return，task/trace 停留 running，控制台永远显示"运行中"。→ turn_body 所有退出路径统一 finish task＋finish trace；客户端至少收到一个 Error 事件。预防见横切 4。
4. **DeepSeek 平台事故（500，15:04 起）**：12 次实测 75% 挂 15s→500、17% 200 后无响应体；先怀疑本地（代理/端点/key 截断）逐一排除后才确认是平台事故。教训：**供应商事故排查先做自身对照实验**（换端点、换 key、查官方 status 页），不要先改自己代码；事故期间要有页面一键可切的备选供应商。
5. **重试边界**：只在"瞬时错误 且 尚未吐字"时重试；已流式输出后重试＝客户端看到重复内容。首事件超时（35s）兜"200 后挂死"；ping 用独立更长超时（45s），不能复用对话超时。
6. **本地大模型是资源决策**：27B 在 Mac 内存占用过高，实测后弃用换 GLM flash。模型选择不只看效果，先算目标机资源预算。
7. **回答首部空白**：本地模型爱以 `\n\n` 开头，入库与 Answer 事件前 trim，否则 TTS 念空拍。
8. **事件名要对应真实退出路径**：`loop_budget_exhausted` 曾误标非预算耗尽的失败，误导诊断。事件命名即文档。

## M2 虚拟 dot2-d 与语音形态

1. **喊停竞态（用户报告，本轮最大坑）**：合成中的旧答案在喊停后仍播出。根因三层：任务已 Completed，取消标志拦不住"已答完未播"的答案；旧轮 TurnEnd 清掉了新轮 `current_task`；"完成"时点被混用（横切 1）。修复＝**停止纪元**（epoch，按设备递增，合成返回后核对）＋每轮任务归属（own_task 不再读共享态）＋TurnEnd 守卫（只清自己的）。
2. **按键入口≠语音入口**：话语入口既触发打断又开启新轮，两轮的播放归属必须分开断言（内容＋任务 id 双重区分），按键回归通过不代表话语入口正确。
3. **收集到首条播放即返回会漏重**：晚于窗口的重复播放捕获不到。→ 收集到该轮 turn_end＋静默排空再统计（`collect_plays_until`），断言写"恰好 N 条"而非"至少 1 条"。
4. **无回执＝unknown**：设备不确认时绝不报成功（工具层 `ToolStatus::Unknown`）；无设备时的模拟回执必须标注"模拟"并进 SSE/trace/模型上下文，三处同文。
5. **断线/重连**：连接代（generation）随重连递增，旧代事件只记账；**被取代连接的 teardown 只能释放自己的待回执**，否则误伤新连接的等待方。
6. **火山 TTS 是 NDJSON 流**（非 OpenAI audio API），ttfb ~0.56s：借旧仓实现时只迁移"协议事实与实测参数"，不复制代码结构。
7. **候选不可用要如实记录**：VoxCPM2 在 oMLX 需 `trust_remote_code=True`（服务端配置），解决前不可用就明说，不硬接也不假装支持。

## M3 行为硬化

1. **提交窗口竞态的复现方法**：纪元检查→`hub.play()` 提交之间是同步代码，无 await 点，外部无法插入停止。→ 加**一次性 async 测试钩子**（`set_before_play_submit_hook`，仅测试设置，无锁区域）让停止完整落地在窗口内——旧代码稳定失败（Play 提交、无 Stop 跟随）；修复＝提交后纪元复查＋补偿 Stop（提交是事实，停止必须到达该播放）。注意：同步 hook 会死锁单线程测试运行时，必须 async。
2. **真实模型跳过工具（glm-4-flash）**：高度口语化说法（"现在网上大家都在听的歌，来一个呗"）下模型不调工具，凭记忆编造榜单并谎称"(播放中)"；经典说法正常。→ 确定性测试全绿也挡不住（它们证明的是循环合同，横切 5）。修复：提示词禁止无回执声称外部状态；新增 `scripts/verify_m3.py` 真模型场景（复测 5/5）。预防：**换模型必跑**。
3. **跨轮上下文缺回执**：会话只持久化"[调用 …]"意图行，"刚才放的什么"无法引用播放证据。→ 工具批次后把回执摘要（status/evidence/结果，有界）持久化；S5 场景先复现后修复。
4. **`String::truncate` UTF-8 边界 panic（独立评审 P1）**：回执行截断 600 字节可能切在多字节字符中间直接 panic，且发生在 spawn 的轮任务里＝静默死亡（横切 4）。→ `truncate_at_char_boundary`＋边界单测。预防：CJK 项目里一切字节截断都要过边界检查。
5. **测试自身引入的竞态**：await 一个"需要并发确认才能完成"的 HTTP 响应会把测试任务饿死（探针 4 秒超时如实返回 unknown——实现是对的，测试阻塞方式错了）。→ spawn 请求任务，线上确认后再 join 响应。
6. **配置历史只有摘要＝不可恢复**：恢复需要完整快照 payload（迁移 v2）；**密钥值永不入史**（只记 key_set 布尔），恢复保留当前密钥。
7. **恢复不重放设备动作要线上证明**：恢复后 wire 只见 ModeSet、零 Play/Stop/Volume 的断言，比任何代码审读都可信。配置操作与动作重放的边界用测试钉住。
8. **隔离实例验证法**：新二进制＋拷贝数据目录＋独立端口（HM_BIND/HM_GATEWAY_BIND/HM_DATA_DIR）→ 不动用户运行中的实例，也能用真凭证做冒烟与真模型验证。

## M3.5 Agent 内核调研与 spike

1. **`Url::join` 尾段替换陷阱（genai 自定义端点）**：genai `util_get_service_url` 用 `Url::join("chat/completions")` 拼 URL，base `…/v1`（无尾斜杠）的**最后一段被替换** → 实际 POST `…/chat/completions` → 404。bigmodel 默认端点自带尾斜杠所以 live 一直正常，本地 wire-mock 才暴露。预防：任何 OpenAI 兼容 base_url 配置**必须尾斜杠结尾**；mock 服务器要在 404 时把状态打进错误信息（本次靠 `Cause: Status 404` 定位）。
2. **wire 名双重映射 bug（自己写的适配器）**：genai 回传的 `fn_name` 已是 wire 名（`music_search`），回程误用 `to_wire_tool_name`（点→下划线）而非 `from_wire_tool_name`，live 断言当场抓出（`music.search` 变 `music_search`）。预防：映射函数成对出现时，**方向命名要在断言里写中文注释级别的显式测试**（"wire 名必须映射回内部点名"）；这正是 spike 的价值——纸面评审没抓到。
3. **确定性对照暴露自有客户端缺口**：首事件后空转场景，genai/rig 2.0s 读超时自愈，自有客户端等 20s 服务端放弃才结束——自有"首事件超时 35s"只保护"一个字没来"，不保护"来一个字后挂死"。修复蓝图＝genai `stream_read_timeout` 语义（per-chunk 超时、心跳重置）。预防：韧性断言要覆盖**半途静默**，不只首事件与总时限。
4. **"drop 即取消"要用服务端视角证明**：客户端文档承诺 drop 取消，但连接是否真关闭只有对端能证——wire-mock 记录 connect/close 时间戳（Drop guard），三客户端 6–8ms 关闭成为确定性证据。预防：取消语义的验收证据在对端，不在客户端日志。
5. **候选隔离的工程手段**：spike 用空 `[workspace]` 表脱离主工作区＋`spikes/*/target/` 入 gitignore＋`.gitignore` 不动主仓——"未选型前不引入依赖"红线从约定变成结构保证（主仓 `cargo test` 全绿即证零污染）。


## M4 NAS 打包与 ASR 接入

1. **Apple Silicon 上 cross 官方镜像不可用**：cross-rs 0.2.5 的 `ghcr.io/cross-rs/x86_64-unknown-linux-gnu` 无 `linux/amd64` 之外的 manifest，Mac arm64 docker pull 直接 "no matching manifest"。预防/解法：mac→linux 交叉编译首选 `cargo-zigbuild`（brew 一装即用，31s 出 glibc 2.17+ 兼容产物，SQLite bundled C 代码照常编）。
2. **fnOS 用户主组不同名**：NAS 用户 `yes999zc` 主组是 `Users`(gid 1001)，systemd unit 写 `Group=yes999zc` 直接 216/GROUP 起不来（journal "Failed to determine group credentials"）。预防：unit 只写 `User=`（自动继承主组），或部署前 `id <user>` 核对；起了 216 先查 journal 再猜。
3. **oMLX 模型加载失败有粘性缓存**：加载失败过的模型之后 `/load` `/unload` 都只回缓存错误（unload 甚至报 "not loaded"），admin reload 需要管理员权限——普通 sub-key 清不掉。预防：改完模型目录（补 preprocessor_config.json 之类）后**一次到位再触发加载**；已脏的服务需要重启（共享服务先问用户）。另：HF 转换仓库（moona3k MLX 系）常缺 processor 配置，补文件要从上游官方仓库补，且上游不一定有 tokenizer.json（Qwen3-ASR 上游就是 vocab+merges 形态）。
4. **"探测先行"当场兑现**：asr-plan 留的"先探测 oMLX 是否支持 /v1/audio/transcriptions"在用户下载 ASR 模型后变成零新增基建的接入路径（whisper.cpp 免装）——探测结论要当天写回方案文档（§2/§6/§8），否则下一个会话还会按旧方案装 whisper.cpp。
5. **管理 API 字段名要用真实入口对**：给 `/api/v0/chat` 发 `{"message":...}` 得 422（字段是 `text`），grep SSE 空输出浪费一轮。预防：验收脚本一律从现有测试/前一个验证脚本抄请求形状，不凭印象写。

## G3 协议 v0.2＋dot2 适配器＋首次实机建链

> 本轮错误密度高（用户点名要求完整记录）。分三类：**实机新事实**（G2 取证无法覆盖、只能上机撞出来）、**自己代码里的真 bug**（多数被合同测试/实机当场抓住）、**流程/诊断弯路**。共同教训：对陌生设备的"推断"全部要在第一次建链时按"会被推翻"准备。

### A. 实机新事实（取证没写、上机才知）

1. **TLS 验证名固定为 `echomuse-controller`**：设备按 IP 拨号，Go 客户端却用固定 ServerName 验证——证书 SAN 没有该名字就 BadCertificate。第一版证书只放了 IP/DNS SAN，设备日志一句 `x509: certificate is valid for …, not echomuse-controller` 才定位。预防：异构 TLS 客户端的证书 SAN 要按**对端验证逻辑**生成（本题只能靠设备报错文本，取证文档没记）。
2. **register.device_id 是序列号**（G090L91072732EXG）不是房间名：适配器硬校验 `device_id == "dot2-d"` → 握手秒断（设备侧表现 close 1005 no status，适配器侧连日志都没有——静默 return 的教训见 C-3）。修正＝wire id 只记录、stable_id 走配置。
3. **register.capabilities 是 22 项厂商名**：音量叫 `remote_volume_arc`（无裸 `volume`），音乐通道 `audio_mix` 存在，hw 参考 `aec_hw_ref`/`ref_uplink` 存在。按取证猜的映射（"volume"）会静默丢失音量能力。预防：能力映射表要在首次 register 时**实测回填**，别把草案映射当事实。
4. **设备不回 ICMP**：ping 失败把诊断带偏（以为整机断网），实际 WSS 链路一直健康（seq 稳定上涨）。预防：判断设备在线要用**应用层心跳/流量**（seq、pong），ICMP 对嵌入式设备是不可靠信号。
5. **设备控制面周期性停回 pong >40s**（数据面照常推 mic）→ keepalive 判死断开 → 设备 ~2s 重拨自愈。flush 的 2s 确认窗落在该窗口就如实 unknown。这不是 bug，是设备行为基线；死线参数沿 DOT（15s ping/40s）。

### B. 自己代码里的真 bug（全部已修＋钉测试）

6. **下行帧忘加 `0x02` 头**：`wav_to_device_frames` 返回裸 PCM，发送时没加 speaker 帧头——合同测试"unexpected binary frame"当场抓住。预防：帧格式常量（头/长度/EOS）要跟**解析侧**成对测试，发送侧单测只看长度不看头就是没测。
7. **数据面看门狗量错了时间基准**：从"看门狗自己的启动时刻"起算 60s，帧到达不重置 → 只要 mic 会话活跃，60s 后必杀健康连接——**实机上第一次真撞到**（音乐播放报 no data plane 才暴露）。修复＝Shared 记录 last_data_frame_ms、帧到达即重置；回归测试＝流量持续超过看门狗窗口连接必须存活。
8. **看门狗判死后关不掉连接**：本地 mpsc sender 还在 data_plane 栈上持有，writer 收不到 None 不会退出——判死只是"清了 shared 里的 sender"，连接半死不活。修复＝oneshot 信号让读循环退出→teardown 真正 drop sender→writer 关 socket。教训：**"谁持有连接生命周期"与"谁判定该死"要同权**——判死者必须有一条能到达 socket 关闭的路径。
9. **音量上限比较在浮点比值上**：64/127=0.5039 > cap 0.5 → 正常回执被误判"超限"触发拉回 ping-pong。修复＝在设备自己的 0-127 档位格上比较（level > round(cap×127)）。教训：**有离散刻度的物理量，比较要落在刻度格上**，浮点比值天然有格点误差。
10. **rustls 0.23 多 provider 共存 panic**：tokio-rustls（aws-lc-rs）＋tokio-tungstenite rustls feature（ring）同时入图，`ServerConfig::builder()` 找不到进程默认 provider 直接 panic——且 panic 在 spawned task 里**无声无息**（只剩 Connection refused）。修复＝显式 `ring::default_provider().install_default()`（幂等）。预防：rustls 0.23 项目必须显式选 provider；spawned task 的 panic 要有出口（这次是 eprintln 诊断才看见）。
11. **测试助手把 RIFF size 写成 usize**（8 字节）：`&(36 + samples.len()*2).to_le_bytes()` 类型推断成 usize → WAV 头多 4 字节 → parse_wav 全 None。定位靠独立小脚本逐字节 dump。预防：手写二进制结构的测试助手要**先 round-trip 再用它测别的**；`as u32` 显式落型。
12. **合同测试证书路径**：fixture 放仓根 `tests/fixtures/`，测试用 `CARGO_MANIFEST_DIR`（=crates/gateway）拼路径 → File::open 失败 → adapter task 又是静默死 → 全套 Connection refused。预防：fixture 跟着**crate**走；启动失败要打日志而不是 let 走。

### C. 流程/诊断弯路

13. **静默 return 不留痕**：适配器多个错误路径直接 `return Err`（无 println/tracing），实机排障时适配器日志一片干净，只能靠加临时 eprintln 诊断。预防：对外协议组件的**每个拒因**都要有一行日志（tracing warn 起步）——这次 BadCertificate/device_id 两关都是盲人摸象过的。
14. **ws.next() 是 Option<Result> 双层**：测试里两个 expect 当 Message 用，编译错三轮。小事，但耽误节奏——对生成器类 API 先看签名再写循环。
15. **换证书后没考虑设备退避余量**：设备重试周期 60s（退避后），改完服务端要等满一个周期或主动 kill server 进程（supervisor 秒拉起）。第一轮白等了 ~1 分钟。预防：设备侧重启/重拨的**加速手段**（kill 进程）写进 runbook 当标准动作。
16. **诊断命令本身别带慢操作**：arp -a（DNS 反解）能挂一分钟+，卡死整个诊断链——分层诊断每条命令独立跑、都带超时。

### D. 好的方面（值得延续）

## G4 控制台补全＋LED＋声学标定＋服务上音箱（2026-11-08 凌晨，无人值守夜航）

### A. 实机新事实（上机撞出来的）

1. **macOS 应用防火墙按进程拦 LAN 入站**：hm-core 改绑 LAN 后，设备侧 SYN 被静默丢弃——表现是连接**无限挂起**（无 RST、无 warn 日志），而白名单进程（网关二进制）同端口秒通。诊断口诀：「挂死无声＝丢包拦截；Connection refused 秒回＝端口没人听」。无人值守夜无 sudo 加白——解法＝白名单网关二进制自带 `relay` 子命令做 LAN 前门，核心保持仅回环。

### B. 自己代码里的真 bug

7. **seq 水位跨连接代粘滞**（G5-1 上机当场活捉）：适配器进程重启→hello 空设备表→device_status(descriptor) 再引入设备→seq 从 0 起→核心保留旧水位→**整条 mic 流被丢成 audio_chunk_stale**。hello 播报路径本就重置水位、device_status 路径漏了。修复＝descriptor 到达于新代时重置；回归测试钉死"重启形状"。教训：**两条引入路径必须对称审计**，G3 合同测试只测了 hello 路径。

10. **afplay -v 线性增益毁语音**：−v 6 把 −19dBFS 峰值推过满幅硬削顶，ASR 只听懂"啊。"——增益必须在文件侧做（tanh 软限幅归一化），播放侧永远 −v 1.x。

## G5-2 直占音频组件替换 EchoMuse（2026-11-08）

### A. 厂商内核 ALSA ABI（全部实测，设计文档 §5 为证据表）

1. **主线假设在厂商内核上全灭**：392 字节 hw_params、arm32 ioctl 编码、直接 HW_PARAMS——三个"标准"假设各自换来 ENOTTY/EINVAL。`gateway pcmprobe`（尺寸/编码/布局穷举）＋反汇编系统 libtinyalsa（param_init/pcm_open 写入序列）＋tinypcminfo 约束打印，三件套把 ABI 挖穿。教训：**供应商 Android 内核的 uapi 不能按主线推，找设备上已验证的用户态二进制当布局权威**。
2. **hw_params 只收 refine 过的缓冲**：info/masks 等字段由 HW_REFINE 合法化后才能过校验——tinyalsa 流程（init→refine→钉值→params）不是风格，是硬约束。跳过 refine 按布局填值＝EINVAL。
3. **采集/播放两侧格式枚举不一致**（S24_3LE=bit32 vs S16_LE=bit2）——同一内核同一套 uapi，两侧各自为政。修法＝永远从 refine 结果取掩码、只在歧义时钉位。
4. **原生 64 位路径对该声卡不可用**（系统自带 64 位 tinycap 同样 EINVAL）——EchoMuse 一直走 32 位 compat。**先跑系统工具做地面真值，再决定自己构建的目标三元组**；固件因此定 armv7 musl。
5. **被占 PCM 的 open 阻塞而非 EBUSY**——组件启动＝武装等待、旧主一停自动接管，无竞态；但监督器的"快退"判据要按"进程存活"而非"退出码"设计。

### B. 自己代码里的真 bug（合同测试＋上机活捉）

6. **播放线程 idle 状态机**：live 流暂时断粮（EOS 未到、队列空）被误判 idle 置真，后续 Samples 因 live==true 不再翻转 idle → 样本滞留、StreamDone 永不触发。修＝阻塞判据动态计算（"无 live 流且无待写数据"），不再维护独立 idle 布尔。合同测试钉死。
7. **音量双源真值**：播放线程持私有 volume 副本、VolumeSet 只更新 shared → 增益检查暴露旧值一直在用。修＝单源（shared），42ms 一锁可忽略。
8. **played_ms 整数除法先除后乘＝0**：`bytes / rate * 1000`。先乘后除。
9. **变参 ioctl 的 ABI 陷阱**：libc 的 ioctl 第二参在 musl=int、macOS=ulong——跨平台构建要 per-target cast，包装函数统一。
10. **上行刻度三档校准**：24→16 位取高位（−73dB，VAD 聋）→满幅直映（−19dB，过热）→`>>4`（−50dB＝G4 基线）。**声学标定跟刻度绑定，换刻度必须重校**；逐通道电平扫描先行排除哑通道。

### C. 流程与方向

11. **晨间"无声"事故闭环**：用户实测 LED 亮但无声→排查项第一优先→用户澄清＝当时音量为零；顺带用两级音量 mixer diff 证明 EchoMuse 音量走软件 DSP（零控件变化）——设计 E7 由此修正为我方软件增益。**先问清现场再深挖，但排查中顺手做的实证照常入库**。
12. **架构方向会战中改**：两进程环回设计做完合同测试后，用户拍板吸收式单进程——硬件层/音频数学/测试骨架全保留，只有角色循环重写。**分层抽象（Hardware trait＋纯函数音频数学）让方向修订成本降一个数量级**。
13. **su 建目录的 SELinux 上下文错配**（G4 A3 变体）：su mkdir 的目录里 adb shell 无法写入——删目录由纯 shell 上下文重建。设备侧文件操作"谁的上下文谁创建"。
14. **开机首跑偶死**：监督脚本在极早期 boot（~5s）死过一次、init 重试第二轮成功；kill 行的极早期 ps 行为嫌疑最大，已改 read-split 逐个 kill。加固后干净重启单次拉起（up=5s）。**boot 路径要按"最坏时序"写，init 重试是最后防线不是第一道**。

## G5-2 P 修复轮＋emOS 转向（2026-11-08 夜）

### A. 实机新事实

1. **evdev 单读者**：固件读 /dev/input/eventN 会饿死 Android InputReader＝系统按键全死（用户实测 P1）。正解＝uinput 转发器：EVIOCGRAB 真设备→克隆设备回注一切非自消费事件（注入验证：sendevent 打进真节点→Android 注册的克隆收到 press/release+SYN）。**且 input_event 尺寸按任务位宽**：armv7＝16B 非 24B。
2. **ledcontroller 是 init 服务**：kill 它＝"拉起-被杀"循环（logcat 刷 "untracked pid killed by signal 1"，用户实测 P2）；init 级正解＝`stop ledcontroller`。**推论：FireOS 上与 init 服务抢资源是结构性逆流**——与 dot2-pcm-route 的 HAL 抢 PCM 受控实验同构，共同构成 emOS 转向的根因。
3. **本机 amonet 布局真相**：真 boot＝p10（16MiB），p17/p18（110MiB）是 amonet 弹床——by-name 的 boot_a 指向弹床，别被名字骗。recovery p12＝TWRP 3.7.0_9-bboe2（与客厅机同镜像）；**本机 `adb reboot recovery` 软件路径 30s 即进 TWRP**；客厅机 fastboot 恢复路径失败的经验不可照搬——每台机器的恢复路径各自实证。
4. **TWRP/su 上下文两坑**：su -c 里 by-name 符号链解析失败（dd 报 No such file）→用裸 `/dev/block/mmcblk0pN`；root 写的文件 0600，adb pull 拒绝→先 chmod 644。
5. **还原演练方法论**：写前镜像 SHA→dd 回写→重启业务验证→**整读回宿主机 SHA 对照＝字节级证明**；写相同字节也是真演练（验的是机制与路径，不是数据）；措辞如实＝"曾回写并已复原"，不写"从未动过"。

### B. 自己代码与流程（P 轮）

6. **RAM 日志随重启蒸发**（P3）：监督器每轮退出码＋/tmp 日志尾即时写入 /data 持久日志——取证要活在比事故更长的存储上。加固后三轮干净单次拉起，早期偶死根因未定（如实记录，不冒充已解）。
7. **断网重试日志刷屏**（P4）：每错必打＝噪声；收敛＝首次＋每 10 次＋状态变化才打；离线必须可视（暗白灯，刻意区别于一切语义态与保留绿）。
8. **自测盲区**：我自测 9/9 唤醒即认为完赛，但用户过夜实测命中按键/LED/重启/断网四类真问题——**系统级行为（输入栈、服务交互、电源循环、网络中断）必须进验收清单**，语音链路全绿不等于设备合格。

### C. 方向与文档

9. **在别人管家的平台上抢资源，赢了局部输全局**：FireOS 上每个"接管"（LED/按键/音频/自启）都要与 init/HAL 对抗且被 respawn 拉回；换平台（emOS＝无 Android 用户态）一次消灭整类冲突。架构决策要先看"谁管家中资源归谁"，不是"技术上能不能抢"。
10. **一页纸两轮审查被抓三处**：AEC 基线错抄客厅形态（没对齐本项目"取消主机"前提——抄基线先对目标）；"p10 一字节未动"不准确（曾回写）；物理兜底拿客厅类推（boot 镜像不同）。**文档声称必须与事实逐字对齐；跨机/跨形态经验引用先查前提是否成立。**

## G6 emOS 装机＋平台迁移（2026-11-08 深夜）

### A. 物理门与恢复路径（本机实证）

1. **本机 Mute 门要 ≥30 秒**：客厅机 5s 即 TWRP；本机 5s 松手＝直接回 FireOS（监测识别 build=LVY48F），按满 ~30s 才进 recovery。**白灯＝进门的可见指标**（用户实机确认）。根因未深究（推测 LK 键采样窗口不同，如实记录不冒充已解）。一页纸"不许拿客厅机类推"的规矩在本轮直接兑现。
2. **动作键门两家都通**（客厅与本机都进 fastboot，绿灯指示）；差异在 fastboot 内命令有效性——客厅 `reboot-recovery` 回 FireOS、OEM recovery 被拒；本机只做只读 getvar（product BISCUIT/secure yes）＋`fastboot reboot`（OKAY 干净回 emOS），flash 类未测（写入动作需要时再验）。**两道门互补：TWRP 可 dd＋挂 /data；fastboot 可 flash 更底层。**
3. **TWRP dd 不认 `conv=fsync`**（option disabled）——报错即**没有写**（读回 SHA 未变＝未污染自证）；改朴素 dd＋sync，0.916s/16MiB。工具不支持时报错退出比静默降级安全。
4. **adb shell 不是二进制通道**：su dd 拉 p10 混入 22KB 杂质→哈希不可比；**exec-out 才是**。md5 校验在 su 上下文要用 busybox md5sum（PATH 缺失坑再现）。
5. **su 跨目录 mv 两坑连环**：SELinux Permission denied＋toybox mv 覆盖确认提示把非交互脚本挂死——G5-2 README 的 cp 配方（cp+chmod+rm）就是解药，忘了用绕一圈。**既有 runbook 要先翻再发明。**

### B. emOS 平台事实

6. **exec 链完全复用**：emOS init 受监督地 exec `/data/local/bin/start_server.sh`（after /run/net-up）＝G5-2 已占路径；A/B 槽监督照常、**/data 既有 Android WiFi 配置被 emOS 直接使用**（wlan0 192.168.1.73 无感回归）——平台迁移成本远小于预期，同一颗 armv7 固件两平台跑。
7. **emOS 服务 envp 无 PATH**：init spawn 只给 HOME/ANDROID_ROOT/ANDROID_DATA——/data 脚本必须自设 `export PATH=/sbin:/system/bin:/system/xbin`，否则 tinymix 全 not found。FireOS init 服务有 PATH，**同一脚本两平台行为分裂的隐形坑**。
8. **macOS 串口辨识**：emOS ACM 端口名不含序列号（/dev/cu.usbmodem31101）——先记基线端口快照，新出现的即目标；system_profiler 可对 iSerial。串口＝raw 只读监视＋命令注入两用（无密码文件时 console_gate 直通）。
9. **nptd 对家用路由超时→设备时钟停在 2010**。当前不阻塞（固件↔core IP 直连无 TLS、云 API 都在 Mac 侧）；**C 阶段 core 上机前必须解决**（TLS 全挂）。最小改法＝固件北向取 core 时间 settimeofday。
10. **known-good 首启自动提升**（`rollback promoted rc=0`）——OS 级试探回滚白得，不用自建。
11. **"同一内核"推理省一轮调试**：emOS 复用 FireOS 内核镜像→ioctl 行为可在 FireOS 上预答。64 位原生 hw_params 从真 64 位任务仍 EINVAL（aarch64 pcmprobe）＝内核分发器只认 compat 路径，与任务位宽无关——**提前在 FireOS 答完，不用等 emOS 串口现场**。

### C. codec bring-up 与 mixer ABI

12. **无 HAL 的 DAPM 症状**：健康 ALSA 时钟＋零 RMS＋"成功"播放但无声＝路由未闭→DAPM 断电（EchoMuse routes.go 寄存器证据：NADC/MADC/DAC/输出驱动全掉电）。完整序列＝10 条 DAPM 路由（8 采集差分输入＋2 播放 DAC→输出混音）＋脚本级设置＋amp 无咔嗒时序（静音时钟→amp On→settle→dacUnity）。**老脚本只抄了部分，缺的就是静音。**
13. **mixer ABI 从头文件来不从记忆来**：NDK 头文件 dump 两架构尺寸/请求码（elem_list 72/80B、elem_value 712/1224B、elem_info 272B 双架构同码、long 步长 4/8）＋真机零风险冒烟（读回→写回同值）双向验证。**enum item 名在 info+88（bionic uapi 布局），不是 mainline 文档写的 id.name。**
14. **"逐项核完"落成脚本**：tools/codec_diff.py 按控件名（绝不按 id——内核挪号）三列 diff，31 控件 0 差异；改 bringup 必须重跑。人眼比对不算核完。

### D. 方向

15. **替换者继承被替换者的职责清单**：EchoMuse 退役≠它管的事消失——WiFi 配置、时钟、远程增益、OTA、诊断都是它的隐性能力，必须有去处（网关仓 docs/g6/replaced-capabilities-plan）。**换组件先列它的能力清单逐项认领，否则能力跟着退役静默丢失。**

## G6 AEC 攻坚轮（2026-11-08 深夜，实机三层 bug＋方法论）

16. **硬浮点 ABI 规则（2026-11-08 升格为硬规则）**：交叉编译到带硬件 FPU 的 ARM，target 一律 `*-musleabihf`；`eabi` 只许纯整数场景。本轮代价＝同一代码 musleabi 4.7 chunks/s（38% 实时率）——**是跑不动，不是慢一点**。上机哨兵＝chunks_per_sec ≥12，第一眼查它。
17. **S24 解码的符号扩展，三处实现三种命运**：老 downmix（`(v<<8)>>8`，对）、我的新 decode（漏扩展→半数环境样本钳到 +32767，pre 轨 +15885 直流铁证）、探针（`as i16` 恰好 mod-2¹⁶ 回绕救回，512/512 侥幸对）。**同一物理格式只允许一份解码实现**，第二份必踩第一份踩过的坑。
18. **codec 回环在播放断流时吐满幅垃圾**（32767 平顶＋静默尾 +65 直流）：TTS 突发写期→DAC 断→回环失效。EchoMuse 的 silenceLoop（永久静音时钟）不是可选装饰，是回环的前提条件——**移植别人系统时"看似多余的常驻行为"要查清它保护什么再决定要不要**。
19. **测量轨分责法**：pre/post/ref 三轨＋空房 A/B（AEC 开 −10dB vs 关 −50dB）＋成对样本转储——"谁制造的信号"一次定责，不靠推理循环。**管线问题先造仪表（三轨/探针/对数据），再谈修复**。
20. **跨启动非确定性**：一次启动 ch8 全程静默，同会话重启进程后探针 512/512 正常——疑 codec/DAPM 启动竞态。处置＝dealias lock 状态当哨兵＋如实记录待复现，不冒充已解。
21. **硬件行为变化波及测试契约**：静音常开时钟让合同测试的两处假设失效（EOS 判定被 continue 跳过；增益断言被静音期稀释）——**改播放行为＝重跑全量合同测试**，测试抓到的是真回归。
22. **macOS 应用防火墙按进程路径放行**：借道已被放行的网关二进制（与 relay 同路径）跑 serve-file＝emOS 时代的 LAN 部署通道；hm-core 的 web 目录只能本机。**防火墙规则是部署通道设计的一部分**。
23. **串口是唯一通道时的工具箱**：raw 只读监视＋命令注入＋分块 base64 拉文件（tools/serial_cmd.py、serial_pull.py 已入网关仓）；控制台被前台阻塞进程堵死＝只能物理重启——**跑长任务别占控制台前台**。
24. **native 依赖必须同一套硬浮点工具链（2026-11-08，G6 收口轮立规）**：speexdsp、将来的 opus、任何 C 库——全部用与固件一致的 `musleabihf` 工具链编译。**混进一个软浮点库崩得无声**：不报错、只是整体变慢，最难查的那种病。规则与 lesson 16 配对：ABI 一致性是整条链接的属性，不是每个依赖各自的选择。

## C 阶段：核心上音箱＋UX 批（2026-11-08）

1. **handle_frame 全程持锁——新帧分支绝不可再取 state 锁**（本次最贵一课，真机卡死一次）：`DeviceHub::handle_frame` 的整个 match 都在 `state.lock()` 守卫内运行。WifiState 分支里写 `self.state.lock()`＝同线程重入 std Mutex＝WifiState 一到就全 runtime 死锁（音箱两线程 futex、连回环 curl 都无响应）。修复＝复用外层 `st` 守卫；`tests/wifi_wedge_repro.rs` 永久钉死该场景（客户端中途断开＋迟到 WifiState＋核心必须继续服务）。**规矩：给 handle_frame 加分支时，凡要动 hub 状态一律用 `st`，不碰 `self.state`。**

5. **busybox 细节**：chmod 不认 `+x`（用八进制）；`reboot` 是 bionic 动态二进制跑不起来——用 `busybox reboot`（串口会掉线重枚举，属预期）。

8. **进程名＝current**：A/B 槽以 `current` 符号链接调用，进程 comm 就是 "current"——`pidof core_a` 永远空手；按 `/proc/*/exe` 精确定位再杀。

## D 阶段：T8 回声根治（2026-11-09 夜，无人值守）

1. **自听的「播放中/播后」要用语音日志时间戳分清**：一次 30s 音乐播放内的三个 mic 段（−29.7/−8.6/−5.6s 处）全在**播放中**，播后只有空段——播后盲窗救不了播放中回声。只看计数器增量会把两者混掉（电池 2A/2B 的 ±1 假象全是分段跨窗记账，时间戳才是真相）。

    - **纪律**：唤醒测试**间隔 ≥35s**（30s 跟随窗会把后续唤醒计成 followup_turns 造成假 miss）；到达级验证要在**播放期间**采样 `/api/v0/mode` 的 mic levels（电平环 ~8s 就滚过去了，播完再查全是底噪）；正常到达级参考＝mic max −14~−16dB。

14. **aec-measure 双轨的三个连环坑（2026-11-10 三轮「真声素材」全废的教训）**：①双轨 **120s 封顶**（从固件北连起算）——settle＋等窗口的流程若超过 2 分钟，目标事件根本不在轨上；②下次 `--aec-measure` 启动会**截断旧档**——部署/重启链里监督器 shell 内存里还持着旧 `AEC_FLAG`（文件还原≠运行值），一次「意外带 measure 的重启」就把刚录的档清零；③拉档前先做**能量 sanity**（整轨峰值＋>−50dB 块数）——一轨全静默＝拉错了 boot 的档，别拿去出结论。取证采集＝重启→立刻（北连后 <60s）打刺激→立刻拉档，中间不许任何其它重启。
15. **跨四层 shell 的命令别用精细引号（本日最大假阴性源）**：`bash → serial_cmd.py → tty → mksh` 四层转义后 `grep 'keyword\":'` 收到的模式带了字面反斜杠——永不匹配。KWS 前半段「全部不命中」的结论全是这个假象（zh_3 原版、纯零前导、TTS 全部被冤枉），落文件＋`grep -c start_time` 裸子串复核后 5/5 确定性命中。**跨层判据要用最笨的形式；任何「意外的一致失败」先怀疑测量链路再怀疑被测物。**
16. **emOS 传文件与跑 glibc 静态 PIE 的两条新路（2026-11-10 验证）**：①busybox `nc -l -p 8944 > file`（设备监听）＋Mac `nc IP 8944 < file`（Mac 外连）＝绕开 macOS 应用防火墙（只拦入站）的 LAN 传输道，MB 级秒到、md5 校验；串行 base64 只留给小文件；固件上传口有 ELF 校验不能当通用传输。②官方 aarch64「静态」二进制多是**静态 PIE＋glibc 动态加载器**形态，emOS 没有 `/lib/ld-linux-aarch64.so.1` 直接 exec 报「No such file or directory」——从 Debian libc6 抽 loader＋libc/libm/libdl/libpthread/librt 五件随包，`./ld-linux-aarch64.so.1 --library-path . ./prog` 跑通。
17. **fw_restart 的监督器定位要认「固件的父进程」而不是「ppid=1 的 start_server.sh」**：主监督器死后其日志裁剪子壳被 init 收养（ppid=1、cmdline 仍是 start_server.sh），按 pid 序 head -1 永远先撞上孤儿壳——TERM 打空、等不到新固件。已修 `tools/fw_restart.py`（awk 取固件 ppid），2026-11-10 咬了两次后修的。
18. **长答案 12s 处句中硬切＝v0.3 有界缓冲撞顶，不是杂音（2026-11-10）**：TTS 合成 ~2× 实时，pushed−played 增长无界，10s 超前上限在 ~12s 撞顶→flush 硬切＝无淡变 click（取证：−13dBFS→数字零 <5ms）。「讲故事必挂」类症状先查 `stream_overflow`。上限已提 60s（0.0.8，合同同步）；核心侧按播放进度配速＝T3.5。
19. **KWS/唤醒类离线复测，刺激链质量是第一变量（2026-11-10 spike 附带确认）**：sherpa 3M zipformer 对录音棚 TTS 5/5 确定命中、对摄像头外放→设备实录链零命中（阈值 0.02 也不中）——而同一素材 ASR 也只听出「高达」丢「你好」。凡「模型不识别」先让 ASR 读同一素材做质量仲裁，真人声永远是最后一测。

20. **用户判听/体感结论入档必须钉住「当时在跑的二进制版本号＋时间点」（2026-11-10 销案教训）**：0.0.7「用户实测杂音仍在」的交接记录实为误记（用户当晚澄清上次会话就已消除）——一条没有版本锚点的负面结论让下个会话把已修好的问题立成头等，烧掉半天分层取证（虽然取证顺带活捉了 overflow 真 bug）。修复类交接写法：「vX.Y.Z 上用户确认：症状已消除/仍在」。
21. **有界缓冲类设计要问「上游会不会天然超速」（2026-11-10 overflow 两层修复）**：v0.3 的 10s 超前上限假设发送方≈实时，而 TTS 合成 ~2× 实时——任何上限都只是把撞墙推远（10s→60s 后真长故事照样断）。正解＝发送侧配速（ahead 预算＝恒小于接收方上限）：核心 TtsPiece 队列＋`TTS_AHEAD_LIMIT_S`=30s。鉴别症状签名：**「答案在固定时长附近句中咔哒断」＝撞上限，不是杂音**。

22. **「用户以为不可配」先查标签而不是先加功能（2026-11-10）**：用户问「唤醒词能否配置」时，唤醒词从 G4 起就在模式页可编辑——真正的问题是「唤醒词」与「唤醒应答」两张卡的说明文案太像，用户把应答词当成了唤醒词。功能已存在时的第一动作＝核对 UI 措辞，不是加第二套入口。已把两卡文案改成「叫醒要说的话」/「叫醒后先说的短句」。
23. **固定短语/硬编码文案要么进设置要么写明理由（2026-11-10）**：退下应答「好嘞」作为 `RETREAT_ACK_PHRASE` 常量存在了两周，用户一问「能否改」才发现是唯一不可配的本地播报。规则：凡设备会出声的文案，默认入 VoiceSettings（含预合成链＋历史/恢复链），常量只留给「改了会破坏匹配」的东西。
24. **多供应商兜底的硬边界＝「主供应商是否已吐字」，不是「是否失败」（2026-11-10）**：兜底判定必须在**已向用户流出 token 之后禁止**——否则同一轮会出现两个半截答案。实现点＝重试循环里记录最后一次失败的 `deltas_emitted`，兜底分支要求 `!gave_up_with_deltas`。测试两条：接力成功＋吐字后零兜底请求。
25. **emOS busybox tar 没有 `--strip-components`（2026-11-10 血泪）**：我照桌面习惯写了「rm -rf assets && tar xzf … --strip-components=1」，结果 tar 在删除后失败＝控制台被清空。emOS 上传物正确姿势＝解到 `/data/local/tmp/xxx` 再 `cp -rf xxx/dist/. /data/hm/web/`；且**破坏性操作前先备份**（本次靠 tar 包本身救回）。

26. **模型测试的切段必须用「内容锚点」而不是「能量阈值」（2026-11-10 差点误杀 KWS）**：用 >−45dB 能量段切真人语音做 KWS 测试，19 段全零→判 NO-GO；实际是阈值段落在设备应答音/退下词上，真短语被切在边界外/切碎。**先 ASR 滑窗定位短语、再按定位点重切**后 5/5 命中。两条硬规则：①切段后先让 ASR 读一遍，读不出字＝坏素材，不要拿去测模型；②「全零命中」这种整齐的失败先怀疑素材与测量，再怀疑被测物（与 D-15 同源：一致的失败先查工具）。

## D 阶段：硬件批＋T2 流式实测（2026-11-10 深夜）

27. **`definite` 不是提前量**：火山流式的首句 definite 与最终文本**同时到达**（唤醒 388/976、退下 454/1038ms p50/p95），真正早出现的是 `definite=false` 的 volatile partial（现场实测：605ms「你好，高达」在 260–340ms 只转出「高达」）。**用 definite 做意图判定＝拿不到流式收益**；要 200ms 级只能靠端侧 KWS。测量口径写死（用户要求）：t_intent 只看 definite，不拿 partial 冒充。
28. **流式短句会吞字，准确率必须分类别看**：同一批 30 条唤醒/退下语料，火山流式 CER 3.9–4.2%、归一化全等 86.7–90%，批量 0–1.2%／96.7–100%——「你好」被吞是系统性现象，不是个别样本。只看命令句（3.9% vs 0.7%）会低估差距。**换 ASR 口要按类别出表，不能只报总体。**
29. **发送节拍必须等于实时**：bench 用 0.9× 实时发送，长句的「语音结束」基准被抬高 10%，t_final 出现 −42ms 的负值伪影。改 PACE=1.0 后长句 t_final p50 658ms/p95 2585ms 才对。**任何「相对语音结束」的延迟指标，先确认发送节拍。**
30. **并发探测把服务端正常关闭当失败**：火山在最终结果后发 1000 (OK) 关闭，我的探针把 `ConnectionClosedOK` 记成 fail，三条并发全判失败——实际全部成功（各 42 帧）。**测量工具自身要先自检：正常关闭＝成功，只有 error-frame 才是环境问题。**
31. **自放音源测 TDOA 是退化布置**：用设备自己的扬声器做 7 麦到达时差，几何上各麦几乎等距（实测 0–2 样本＝≤4.3cm 路径差），不能据此说「阵列没有方位能力」。**要测用户方位必须用离轴人声**（本次未测，如实标注）。
32. **ch7 不是麦克风**：静音播放时 ch7 精确 −120 dBFS（数字零），播放时比最热麦还热 14 dB——第二条硬件环回。9ch 语义精标又前进一步（ch7/ch8 都是环回类，ch0–ch6 是麦）。
33. **tmpfs 探针轨要有上限意识**：/run 只有 4MB，单轨封 960KB → 9ch 只能存 3.3s。用 28s 素材测阵列时窗口只覆盖前 3.3s（电平可用、噪声底不可用，得另放静音素材测底噪）。**短窗口测量要配一个静音对照，否则 SNR 是假的。**
34. **两会话共用一个仓库：禁 `git add -A`**（用户 2026-11-10 提醒）：另一会话的 `git add -A` 把本会话的 cpu.rs/绑核 WIP 卷进了 docs 提交（2836beb，代码没丢）。**提交一律显式路径**；发现自己被卷时在说明里认领，不回滚。
35. **`?restart=false` 也会翻 `current` 符号链**：§12 的 `write_slot` 负责翻链，`restart` 只决定要不要 TERM 监督器。想「只暂存不生效」是做不到的——暂存后运行中的进程仍是旧二进制，**任何一次意外重启都会启用新槽**。要控制部署时机就一次做对：上传＋重启一起。
36. **常开的诊断探针会吃掉音频确定性**：加完 ch8/9ch 探针后以「稳态常开」跑了一轮，chunks/s 出现 8.8–11.3 窗口（正常 12.5–13.4）——三轨 tmpfs 写入在播放期形成 I/O 尖峰。改成**按需武装**（核心 touch `/run/hm-loop/arm`、固件在播放起点检查、读完即删）后恢复正常。**诊断设施默认必须零稳态开销；想常开先拿 chunks/underrun 数据说话。**

## D 阶段：T2 复核与测量纪律（2026-11-10 深夜，用户验收后追加）

37. **两个变量同时变就别写归因**：首轮把「火山 bigmodel＋流式」与「硅基/oMLX＋批量」比出的 CER 差距写成「流式/模型变差」是错的——模型与接线方式同时不同，oMLX 根本没有流式口。**结论只能写成端到端对比**；要归因必须同模型双模式（当前火山无批量权限，做不到就明写「无法归因」）。
38. **流式短句吞字＝起步上下文不足，不是模型能力**：给 300ms 前导后，「你好」回来了（唤醒关键词率 96.7%→100%，命令 CER 4.07%→1.69%）。**任何流式 ASR 的短句 CER，先做 pre-roll 再下结论**。
39. **前导要 burst，不要 paced**：把 300ms 静音按实时节拍发送，整条流被推后 → t_final +200ms（578ms）；一次性 burst 发送 → 236ms（比无前导还快）。**"补上下文"和"推迟音频"是两件事，别用同一条时间轴。**
40. **测量脚本自己的口径也会制造 CER**：数字 ITN（「10 分钟」→「一零分钟」逐位映射）给命令类贡献 ~0.7pp。**报 CER 前先核归一化映射**（多位数、单位词），否则会把工具缺口记到模型头上**。
41. **ch7/ch8 定名靠比值不变性**：两路都是数字零（静音时 −120dBFS）、互相关 lag 0/corr 1.0、电平差稳定 −24dB（≈÷16＝S24→i16 的 `>>4`），改音量比值不变 → 同一路环回的两个数字刻度，不是两路不同环回。**判断"两路是不是同一信号"：看比值随增益是否恒定，而不是看绝对值。**
42. **0.6B int4 的"330–360MB"是权重算术**：实测 `mlx-qwen3-asr` 0.6B-4bit 加载＋一次转写 RSS **898MB**（MLX）。**内存数字必须区分"权重"与"运行时峰值 RSS"**；用户要"更硬"就给实测，别拿估算当结论。
43. **VAD/阈值类行为变更要有证据门槛**：120s、6 句就建议 640→400ms 太薄（用户否决）。新门槛＝≥10min 真实语音（含犹豫/停顿/拖长音）＋「退下……吧」词后停顿，**误切率 <2%** 才落，落地后真机复测时延。**省 240ms 的收益 < 误切一句话的代价。**
44. **HANDOFF 里"结论"要随复核改**：T2 从「闸门 NO-GO」改为「接线方式需修正」是用户复核推翻的，文档必须同步改口径（不是只在回复里说）。**负面结论被推翻时，先改文档再谈下一步。**

## D 阶段：T4 关键词打断（2026-11-10 夜）

45. **「打断后声音还在」先查 stop 到没到 DAC，不要先怪模型**：整段 WAV 播放的 Stop 只回了回执、声音照放——根因是播放线程的 **burst 写循环**（把排队样本一次写完）+ **命令通道每轮只取一条**，Flush 排在 117 条样本命令之后。判据用固件自己报的 `PlayFinished.played_ms`：被打断的播放应为 0（走 FlushDone），放完才是时长（`28032`）。**"回执=device_confirmed" 不等于"声音停了"**。
46. **验收第 3 条（降级链）要在目标平台上先确认那个键真的接了**：`KEY_HELP`（顶面圆点键）在 emOS 直占形态原来落到 `Unknown`——动作键根本没接停播，这条验收在改之前不可达。**凡"XX 仍可…"的验收，先在目标形态上把那条路走一遍**，别拿 FireOS 形态的历史验证冒充。
47. **延迟数字先写死口径再出数**：句子结束用「段内峰值 −12dB 的最后一帧」（段内是 AEC 残余，绝对底噪门限会被残余淹没）。同一批数据：−12dB→P50 300ms、−16dB→290ms、−20dB→80ms（把残余当语音，不成立）。**换门限能换出任何结论，所以口径必须先钉死并一起报**。
48. **模型自带的 token 时间戳不可信**：同一素材模型报 last_token=0.84s，声学位置在 2.5s——`detect_ms` 这类"模型自报延迟"会给出 16s 的荒谬值。**延迟只能来自同线程、同时钟的物理轨道**（本轮用 aec-measure 的 pre/post：同一次 capture 循环写出，天然样本对齐）。
49. **测量设施本身可能把整机搞挂**：measure 双轨持续写 /data（64KB/s）与 MTK 看门狗复位（`wdt_by_pass_pwk`）相关，4 次复位里 3 次在「measure＋播放/KWS」。**仪表要短窗、要能关**；长跑（浸润/稳定性）一律关掉。
50. **喂料粒度也是延迟**：KWS 只能在拿到样本后判，按 80ms 上行块喂最多白等 80ms；改 20ms 切片（本轮实测不改变 P50，但这是唯一"不花任何代价"的余量，先拿掉再谈别的旋钮）。
51. **误触发要分"自放"和"房间"**：播放中的命中才是自触发失败（会停播），空闲时的命中只是房间语音（记录不动作）。报告时分开计数，别把两件事混成一个"误触发率"。

## D 阶段：T4 后的缺陷台账与判读（2026-11-10 夜，用户裁定）

52. **「整段播放不可打断」是回执语义骗了人，不是模型/门控问题**：固件对 Stop 回 `device_confirmed`，但写循环把整段排队样本一次写完、命令通道每轮只取一条，Flush 排在 117 条样本命令后面。**判据只能是固件自报的 `played_ms`**：被停掉＝0（FlushDone），放完＝时长（StreamDone）。同类"停不下来"先看这条。
53. **「XX 仍可…」类验收必须先在目标形态上走一遍**：`KEY_HELP`（顶面圆点键）在 emOS 直占形态原来落到 `Unknown`，动作键根本没接停播；FireOS 形态的历史验证帮不上忙。
54. **T2 为什么不接线（写明白，供以后研究）**：不是"流式/模型不行"——归因已澄清为**起步上下文**（300ms burst pre-roll 把 CER 3.9–4.2% 拉回 1.1–1.7%、唤醒关键词 100%、t_final 180–236ms）。不接线的真实原因：①判据仍未严格达标（唤醒 p50 236ms、退下 p95 759ms）；②**没有产品需求**——现网本地批量 ASR 更快更准，而"说完才知道"这个真痛点靠流式 ASR 解决不了（definite 不早于 final），要靠 T1 turn detection / 端侧 KWS（T4 已做）。以后若要重启：必须 burst pre-roll、退下词单独调、并按类别出 CER 表。
55. **看门狗复位（`wdt_by_pass_pwk`）先记缺陷、不猜修**：本轮 6 次，负载谱系从「大文件拷贝」到「measure 持续写」到「稳态连续播放 ~19 分钟」；`/proc/last_kmsg` 空、无 pstore，机制未证。**用户裁定：记录为缺陷，等真实使用中复现再带日志排查**；禁忌：长跑不开 measure、不拿反复杀 KWS 当压力测试。它的存在也决定 **3h 连续运行必须等缺陷修好再跑**（否则白跑）。
56. **VAD 误切的历史「0/6」不可复现**：素材在 `/tmp`（易失）、口径是"锚点窗口内出现 ≥2 段"（带 pad 的宽窗口恒为真）。新口径＝**ASR 紧锚点 + ≥2 段各覆盖该句 ≥150ms**，并同时报首尾削。**凡"某指标历史值"，必须同时留素材与口径，否则等于没有。**
57. **自放的 TDOA 不是 0，是按通道分组的固定偏移**：GCC-PHAT 在 7 麦上给出 max|lag| 2.91 样本，但组内≈0、组间 ~1.4 样本台阶（G0{ch0,ch1}、G1{ch2,ch5,ch6}、G2{ch3,ch4}）——是 ADC/通道组的固定延迟，不是声学。**任何方位估计前先标定分组偏移**，否则近场会被判成有方向。

58. **复位间隔缩短到分钟级＝阻断项，不再是"待复现"**（2026-11-10 夜 20:27 追加）：`wdt_by_pass_pwk` 连续 7+ 次，最近两次 boot 间隔 10.6 分钟与 ~3.7 分钟，**空闲（只有房间说话被转录）也复现**；观测量：温度 35–41℃ 正常、`/proc/last_kmsg` 0 字节、`/sys/fs/pstore` 不存在、dmesg 每秒约 1 条 `syscall 403` 刷屏。**纪律**：①不要凭猜改；②未解决前不排长跑（3h/≥10min 录音/30min 音乐浸润都会白跑）；③每次只改一条并留档。**用户 2026-11-10 决定：这是新会话的第一位任务，先给问题、不在交接里预设方案。**

## D 阶段：P0 看门狗复位的根因（2026-11-09 夜）

59. **旧内核不认识的系统调用＋串口 console＝整机复位，不是"负载/杂音"**：armv7 固件
    （musl 1.2，64 位 `time_t`）每次 `clock_gettime` 打 **`syscall 403`
    （`clock_gettime64`）**，3.18 内核的 AArch32 compat 表没有这个号 → MTK `traps`
    补丁打 **24 行/中位 1.24KB** 的寄存器 dump（实测 2.29 次/秒、3.14KB/s，启动时能
    90ms 内连打 8 次）→ 写 `console=ttyMT0,921600` 时 console 驱动**关中断**排空 FIFO
    → 音频 SPI 的 **100ms 传输超时**（崩溃前最后一个 dump 与超时相隔 **98.9ms**）→
    厂商 `spi_data_read` 错误路径空指针（fault 0x10）→ 内核死在软中断里 → 硬件看门狗
    `wdt_by_pass_pwk` 复位。**修复只动二进制**（不动内核、不调 printk）：
    公共 `clock_gettime` 改走内核实现的 32 位 263（`clock32.rs`）；`Path::exists()`
    （musl 走 `statx`＝397）改 `access(2)`；核心 `fs::metadata`（`statx`＝291）改
    open/lseek/read。**别用 `console_loglevel=0` 绕过**——它连 `ram-1` 一起静音，
    下次崩就真没现场了，而且内核脆弱性原封不动。
60. **有界内核环形缓冲里的"总数"不能证明不再发生**：403 dump 把 64KB 环填满后，
    `dmesg | grep -c` 会饱和甚至下降（本轮 96 → 90 → 89），看起来像"好了"，其实
    只是被挤出去。**判据要取"最新一条的时间戳 vs uptime 的差（age）"**：age 单调
    增长才等于"没有新的"。修复后 403 归零、残留的 397（statx）也被 `access(2)` 拆掉，
    age 从 0 一路涨到窗口结束。
61. **"没有现场"先怀疑取证口径，再怀疑硬件**：交接写「`/proc/last_kmsg` 0 字节、
    无 pstore，所以没有崩溃现场」；本轮连续三个 boot 都读到 **64,622 字节**完整崩溃链
    （ram console 一直注册在 `/proc/consoles`，少的只是 pstore）。**同一台设备上
    "某个文件是空的"要在 boot 后不同时刻复核**；`/proc/consoles` 一行就能看出内核
    console 在往哪写（本轮：唯一的串口 console 是没人读的 `ttyMT0`）。
62. **起爆点未证就写"未证"**：机制链每一环都有日志/时序证据，但"为什么 11-09 才开始"
    没有 0.0.14 之前的 trap 速率留档（老二进制被 A/B 两槽覆盖），只能列候选（cpu1
    绑核、T4 的写循环/KWS 旁路）。**拆掉放大器就足以让复位消失，不需要先证明起爆点**；
    文档里把"机制已证"和"起爆点候选"分开写。

63. **「计数器动了」不等于「功能通过」——验收判据本身会造假**：T5 语义打断用
    `barge.stops` 增量判成功，而实现缺陷造成自激循环（设备反复打断自己的回答），
    3 轮真人说话把计数刷到 **17**，任何一轮都必然 `stops_delta>0`，脚本于是报
    「3/3 通过、P50 120ms」。**用户真人体感是「一直卡」，当场否定**。判据必须写
    「一次输入 → 恰好一次动作 → 一次完整输出 → 之后静默窗口内零新动作」，
    并把「总数异常放大」「输出碎片化」列为失败条件。**先问体验，再看计数**；
    自激类缺陷会主动把所有计数型判据喂成绿色。
64. **把「与参考低相关」当「有人在说话」是充分/必要条件搞反**：AEC 残余、
    TTS 起始瞬态、房间反射同样与 DAC 参考低相关。T5 打断后清尾盲窗＋开窗豁免
    半双工门控，等于把设备自己的应答放行给近端检测器，形成自激。低相关只能是
    **必要条件**；必须与播放状态机（应答保护期）、能量包络联合判断。开窗前先问
    「这段时间设备自己会不会说话」。
65. **阈值标定别用单点样本**：首版 `corr_max=0.65` 来自「回声 0.652 / 近端 0.214」
    两个观测，真机一跑就出现回声 0.651（距阈值 0.002）；改成 0.50 后回声最低
    0.509，余量仍只有 0.009。要分别采「纯播放」「真人说话」「TTS 起始瞬态」三组
    分布，取能分开且两侧各留 ≥0.1 的值。**并且 R1 未修时调阈值是隔靴搔痒**——
    先修状态机，再标定阈值。

## D 阶段：T5 修复与验收（2026-11-10 凌晨，真人两轮）

66. **「整轮」和「一句」是两个不同的完成粒度**：流式回答里每句都是一次新的 `speak_stream_segment`，
    如果它每次都重新读 stop_epoch，停止后的下一句就被当成「全新的一句」照常播放——用户听到
    「说半句、掐掉、再说半句」的「卡」。**停止纪元必须在轮到开始前锁存**，一次打断作废整轮；
    但别用「丢弃 agent 流」来实现（会丢 `turn_end`，验收与审计都对不上）——让事件流走完、
    只吞掉 Token/Answer 的播放动作。回归测试要造「句间空档」：新增 `Scripted::TextPaced`。
67. **打断前滚会把设备自己的声音送进 ASR**：前滚录于「本方播放期间」，带 AEC 残余；回灌后
    ASR 把设备刚说的话转写回来（「我在。」正是上一句答案的残余），核心再当成新指令回答——
    这就是用户说的「自问自答」。**假触发 + 前滚 = 制造一句不存在的话**；关掉前滚后，
    假触发最多只停一次播。代价（第一个字可能丢）要如实写在文档里，不能只报收益。
68. **「响且与参考去相关」不是「有人说话」**：把 500 ms 采样的三组 corr 分布摆出来，
    echo steady（n=288）min 0.096 / p50 0.530 与 near（n=70）p50 0.299 / p95 0.784 几乎完全重叠。
    **任何阈值都分不开**；能分开的是播放状态（起播窗/应答保护期/参考是否锁定）。
    「低相关」只能是必要条件——这次用数据把这条钉死了。
69. **先怀疑播放链的非线性，再怀疑检测器**：真机上「设备自己的声音像人」的物理来源是
    **响度链路的限幅失真**——AEC 是线性的，抵消不掉失真产物。A/B（56 s 无刺激）：84/127
    loudness-on 4 次误触发；70/127 2 次；60/127 0 次；84/127 `--loudness off` 0 次。
    **音量与 DSP 的组合会改变「能不能被打断」**；报告打断指标时必须同时报音量与 loudness 开关。
70. **AEC 参考的锁状态是判据的一部分**：dealias 在播放中反复 loss/relock（30 s 内 relocks
    4→20），失锁时返回的是原始 ch8，互相关失去意义。检测器必须**逐块**拿到锁状态，
    未锁定就不许报事实；这也解释了「为什么有的窗口 corr 高有的低」并不是声学变化。

## D 阶段：收尾轮与测量纪律（2026-11-10，收尾会话）

71. **A/B 的条件顺序会自己造结论**：固件重启后的**第一个** 56 s 即使最终配置也带误触发
    （实测 11 次与 15 次）；同一条件加 2 遍预热后是 **0/0/0**。上一轮 R6 的四条件
    （84-on 4 → 70-on 2 → 60-on 0 → 84-off 0）按误触发升序排列，恰好也是**预热时间升序**——
    「音量越低越安全」里混进了 AEC 收敛。规矩：跨条件 A/B 必须固定预热（或交叉/随机化），
    报告里同时写预热状态。**方向结论（loudness on vs off）在同样预热下仍然成立**，剂量关系不成立。
72. **限幅器必须是"有截止时刻的连续增益"**：按滑动窗峰值每样本把增益瞬间跳到目标＝音频速率
    阶跃（宽带失真，正好加在 AEC 要抵消的信号上）。正解＝单调队列取「在飞窗口最紧需求」，
    用它样本下标当**截止时刻**，增益按剩余样本数做斜坡、准点落到目标（单测：最坏单步
    < 总降幅 10%）。数值坑：比较用严格 `>` 时，周期信号相邻峰值的浮点差（0.89130 vs 0.89129）
    会把旧期限挤掉 → 斜坡永远差一点（实测 0.984 vs 0.891 上限）；比较必须带 eps（1e-4）。
73. **前视延迟线要在段结束清空**：不清空＝上一段最后 5 ms 在下一段开头重放一遍，同时这一段
    丢掉自己的尾巴。现在两通道都空时 `reset_stream()`；丢的尾巴落在收尾淡变里，听不见。
74. **`barge-args` 只在监督器脚本启动时读一次**：`POST /firmware/audio?restart=true` 只 TERM
    固件子进程，监督器不重启 → 新二进制仍带着**旧旋钮**（本轮表现：部署了 0.0.20 却仍在
    `--loudness off`）。改旋钮后必须 `fw_restart.py`（TERM 监督器本体）。这条与 D-35
    （`?restart=false` 也会翻 `current`）配对：**翻链、重启子进程、重读旋钮是三件独立的事**。
75. **诊断仪器能把 `/run` 写满并让固件退出**：`/run` 是 4 MB tmpfs，环回探针三轨上限
    960 KB/轨（≈2.9 MB）＋固件日志；写满后固件 `exit 101` 且**没有 panic 文本**（stderr
    也写不进满的 tmpfs）。本轮两次，都是我制造的（切片 288 KB×2 叠在探针轨上）。
    规矩：探针按需武装、切片用完即删、长跑不武装；固件侧应改成"探针失败只丢诊断＋水位保护"。
76. **先问资源归谁，再谈能不能抢**（AP 模式的一条死路）：WiFi 归 init——`wpa_supplicant`
    是 `/init` 的子进程、`kill` 即重生（pid 513→4718→4852）；emOS init 没有属性服务表，
    `stop wpa_supplicant` 无效；自带 wpa_supplicant 不认 `set_network … mode 2`
    （6 s 后 `wpa_state=SCANNING`，仍在当客户端）；`hostapd` v2.3 是真二进制，但
    `-dd` 也**零输出、退出 1**。结论＝要 init 钩子/镜像改动，不是多花时间能绕过。
    与 G5-2 的 FireOS 教训同源：**在别人管家的资源上硬抢，赢局部输全局**。
77. **"没有播放"的启动哨兵不是"通过"**：安静 boot 全部 `first_play_corr=n/a`，
    `ch8=false` 是"没播放所以没得比"。给矩阵加"每次重启后立刻放一句"，4 次窗内落播的
    boot 全部 `corr=1.000`。报告里 `n/a` 与 pass 必须分行写。
78. **控制台"能看能改"要逐参数过**：`barge_protect_ms` 从 T5 起就能 `PUT /mode`，页面只有
    显示没有编辑（本轮补滑块）。判据不是"有卡片"，是"**每个可调参数都能在页面上改**"。
    顺带复发了 M4 的老坑：音量 API 收**线性 0..1**（不是 0…127），422→400 两次才定位——
    请求形状一律从既有测试抄。
79. **A/B 表要写全"当时武装了什么"**：预热、探针是否武装、音量、loudness 开关、固件版本、
    条件顺序。本轮 1.1 的结论之所以能推翻上一轮的一部分，就是因为补了"预热"这一列。
80. **长跑要同时看两条链**：设备侧（`/proc/uptime`、traps age、SPI/oops）与核心侧
    （generation、chunks/s、voice log）。只看核心会被"监督器把固件拉回来了"骗过——
    一次固件重启在核心侧只表现为一次 `device_status`。
81. **退出码 101 但没有 panic 文本时，先看日志能不能写**：tmpfs/磁盘满会让 stderr 也失败，
    现场只剩半行日志。先查水位，再怀疑代码路径。
82. **"未达标"就写未达标**：响度阶梯在 84/127 下 3 轮×56 s 仍有 11/0/0 与 15/0/0 的误触发，
    关闭后 0/0/0。结论句只能是"保留关闭＋列出未竟"，不许写成"基本修好"。

## R1 自听回灌（2026-11-12 日间续）

85. **近端判据必须相对参考，绝对 dBFS 门限会在真实音量下必然误触发**：124/127 下 AEC 已经
    工作（residual −17.9 dB）时，残差仍有 −37.3 dBFS，高于旧的绝对 −45 dBFS onset；旧代码
    把它当“人”。改成 `energy >= ref − 15 dB` 后同一段不再触发。D-84 早就写了“相对参考”，
    这一轮是它的现场证明。**绝对 floor 只配挡数字静音。**
86. **AEC 的 ERLE 是时间曲线，不是常数**：同一台机器、同一摆放，起播 0–2 s 只有 4.6–14 dB，
    4–5 s 后才到 24–33 dB；归档的 22.8 dB 是整段中位数。**检测器如果直接信残差，就会精确地
    在起播前几秒开火**；更糟的是误停把回答掐在 1–2 s，滤波器永远到不了收敛段——自激循环。
    修法是“收敛门”（连续 5 个回声块 ≥15 dB 才允许 fact），不是把 settle 从 600 ms 调到 3000 ms。
87. **多麦阵列的“回声相关性”没有想象中可靠**：7 麦朴素平均在 124/127 的回声窗口只有
    corr 0.1–0.4，fusion 后 0.4–0.8；而 AEC 残差相对参考是 24–33 dB。**守卫的 corr 只能当
    第二道线，第一道线是“残差相对参考”**；把 corr 当唯一充分条件，就会在自己身上翻车。
88. **永远不要把一个已知坏的参考喂给自适应滤波器**：dealias 失锁时 raw ch8 是别名（48k 每 3
    取 1、无抗混叠），AEC 拿它当参考学，残差≈参考；同时守卫用 raw ch8 算相关，相关性天然低。
    正确回退是**从输出环的上一已知位置 coast（或送零）**，并且按 20 ms 帧报 `Degraded`，
    不是 80 ms 块末读一次 `locked`——块内失锁+重锁会被漏掉。
89. **“停播”和“成句”必须分开**：接受 barge-in 后立即停播是对的；但停止前/停止瞬间的音频
    （pre-roll、stop flush、DAC 环 170 ms、房间混响）是**我们自己的回答**，不能当用户的话。
    250 ms 尾音丢弃＋VAD reset 是结构修法；文本重合度闸门（`mic_suppressed_own_answer`）只是
    临时止损，必须随结构修法一起下线。代价是打断的第一个音节会被丢掉——如实记。
90. **测量口径要对准工作点**：T8 的 ERLE 刺激比真实 TTS 回答轻约 14 dB；“22.8 dB”不是工作点
    上的数。以后凡是“AEC 能力”类结论，必须注明刺激电平、音量、预热状态和逐窗曲线；否则
    整段中位数会把最危险的起播段平均掉。
91. **不要把一次跨设备“延迟”直接判成时钟偏移**：08:33 的 3.581 s 当时没有复现成队列延迟，
    我据此写成“墙钟投影偏移”；2026-11-12 夜间同一设备再次出现 3.078 s，且同一分钟
    `mic_speech_started` 的 ts/ts_ms 只差 1 ms，直接推翻了这个结论。现在只能说“真实延迟，
    归属未定（设备出站/核心事件泵/下行队列）”；结构解是把立即停播放到 gateway，别让 Stop
    排在 TTS 分片后面。`latency_ms` 只能当诊断；排序用设备 mono/seq。
92. **旧核心的 6.3 MB multipart 上传会在 memchr 里 panic**（连接重置）；新核心在本地同一路径
    正常。设备更新路径要有一条“真实大小 payload”的回归测试；现场恢复路径＝Mac `http.server`
    ＋设备 `busybox wget`＋md5 核对＋非活动槽＋原子翻 `current`＋重启监督器。这不是常规路径，
    但必须在 HANDOFF 里留下，避免下一次卡在“上传失败”上。
93. **服务配置是发布态的一部分**：重装/迁库把 ASR 从本地 oMLX 带成云端 SenseVoice，代码没动
    但“叫不动”；唤醒原文“高单”＋严格拼音匹配（`voice.rs:2138`）导致整句丢弃。以后迁
    数据/库/开发配置前，先导出 `services`＋语音模式快照，迁后逐项比对；不要把配置漂移当
    声学问题查。
94. **立即停播属于 gateway 的反射层，不属于 core 的流循环**：长流式回答时 Stop 会排在 TTS
    分片后面（1.9 s 才确认），fact 也可能晚 3 s；EM 在设备本地 `CutReplyOnBarge`。结构解＝
    gateway 本地停播，core 只决定“算不算一轮”；不要在 `speak_stream_segment` 里加 if。

## 如果从 0 重来：我倾向的顺序（个人经验，2026-11-10）

这一节是偏好，不是规范。每条都注明我为什么这么排，以及当时反着做付出过什么。

1. **先定三边界与协议版本**（大脑／设备网关／工具插座）。协议是两仓唯一耦合面；本项目四天
   里边界没有返工，返工都发生在实现内部——G5-2 方向从"两进程环回"改成"吸收式单进程"时，
   因为硬件层/音频数学/测试骨架是分层抽象的，只重写了角色循环（LL G5-2-C12）。
2. **先跑通文本回路，再碰语音**。语音调试时间大约 80% 花在时序而不是语义；M1 一天做完文本后，
   后面每个语音问题都能拿文本路径做对照（trace、取消、工具回执），定位快很多。
3. **尽早让设备"可观测"**：开机哨兵、诊断端点、串口全通道、A/B 槽。P0 那轮如果没有
   `p0_watch` 采 uptime 与 trap age，取证会更久；G6 之前没有 `boot-health` 哨兵时，
   "ch8 跨启动静默"只能靠记忆和传闻（开放了几个月）。
4. **AEC 在真机标定并冻结，顺序是 ERLE→冻结→CPU→VAD**。我试过顺序颠倒，等于全部重测；
   单是 tail 一个参数就把 CPU 从 28.8% 拉到 35.0%（LL G6-1 三账）。
5. **打断分两层做**：设备侧反射（关键词，P50 300 ms）先，核心语义（检测 160–240 ms）后。
   反过来做（先语义）得到的是"计数漂亮、体感很糟"——T5 首轮 3/3 通过、用户当场否掉（LL D-63）。
6. **长跑放在所有音频改动之后**。本项目排了三次才真跑成，每次都被新改动推翻；最后那次才暴露
   每小时 OOM 与近端误触发这两件短测看不到的事。
7. **体验类反馈先分解到机制层，再动参数**。"说话太小"→响度阶梯（响度问题不在 TTS 而在
   输出 DSP）；"一直卡"→整轮纪元（每句重读 stop_epoch）；"自问自答"→前滚回灌 ASR。
   直接照着感觉调参数会绕远（LL D-67/D-69）。

83. **"RSS 一直涨"不等于"程序在泄漏"——先量 live bytes 再看分配器**（2026-11-10 收尾）：
   固件每 28 s 播放涨约 8 MB、约 57 分钟被 OOM 杀死。四刀二分（断北向→RSS 恒定；
   关 AEC／关检测器→速率不变；短片段 0.1 MB vs 长片段 7.9 MB→与**播放时长**成正比）之后，
   装了一个记账全局分配器（`alloc_dealloc`，每播放结束打印 `live = allocated − freed`）：
   **`live` 每次回到 0.41 MB，而 RSS 涨到 11 MB** ⇒ 程序没有逻辑泄漏，是 musl 对 2.7–5.4 MB
   大块的保留/碎片化。教训：`live` 与 `rss` 的差值就是"分配器滞留"，这个数一打出来，
   争论文档里所有"大概是谁忘了 free"的猜测当场结束。**在没有堆分析器的嵌入式目标上，
   一个 30 行的计数分配器就是最好的分析器。**
84. **修一个声学判据前，先确认"改这个旋钮真能碰到那一类样本"**：近端误触发（−42.4 dBFS）
   看起来"门限抬高 7 dB 就能滤掉"，实测提到 −38 后同一轮刺激反而出现 2 次停播 + 多一段
   「哦。」，首个误触发仍落在刺激前（`energy=−31.9` 而 `ref=−13.5`）。**残留在参考很响时
   能量并不低**，所以绝对能量门限对这类样本无效；要看的是"相对参考"（`energy − ref`）。
   结论已退回 −45，并在台账里写明方向。**调参前先看失败样本的分布，不是只看它的均值。**
